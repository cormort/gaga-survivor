```
砲塔 9  傭兵 1  待升級 0
狀態 PLAYING
✖ 每幀例外 ×N                          ← 只有出事才會出現
<錯誤訊息>
<拋出位置>
```

### 0.4 判讀規則

| 面板徵狀 | 結論 | 回報什麼 |
|---|---|---|
| `update/render 0.00` + `跑0幀` + 狀態 PLAYING | **例外凍結**，不是效能問題 | 面板最下方三行 |
| `跑N幀` 正常但 `幀` 數字很大 | 真的效能不足 | 完整面板 + 各項計數 |
| `凍結 x%` 的「暫停」不為 0 | 狀態機卡在彈窗 | 當時的 `狀態` 欄位值 |
| `凍結 x%` 的「頓格」不為 0 | 打擊頓格 | `hs` 欄位數值 |

**`fps` 這個數字單獨看沒有意義** —— 畫面凍結時 fps 照樣是 60，一定要搭配 `跑N幀`。

## 0.5 踩坑清單（**動手前讀完，這些都是實際踩過的**）

### 坑 1：headless 的 dt 會被夾住，直接放大 dt 會穿隧

headless 的 rAF 被合成器壓在 8–18 fps，而遊戲的 `dt = Math.min(0.1, …)` 會夾住上限。
若為了加速而直接放大 dt，會變成 0.4 秒/步，造成碰撞穿隧（上一輪實測：14 秒暴斃、擊殺 0）。

**正確做法**：固定步進，每幀拆成 n 個小子步，邏輯步長恆定。

```js
// 遊戲時間以 K 倍前進，但每個子步的 dt 固定，不會穿隧
const SUB = 1 / 30, K = 4;
for (let i = 0; i < K; i++) g.update(SUB);
g.render();
```

**連帶影響**：這樣跑出來的「幀」「最差」兩欄會被夾具汙染，**不可用**，
只能看 `render ms` / `update ms` 與各項計數。

### 坑 2：不隱藏開始畫面就 `g.start()`

`#start-screen` 的隱藏只是 `opacity: 0`，元素還在。不照真實流程加 `.hidden`
就直接 `start()`，會留一層全螢幕 `backdrop-filter: blur`，**汙染所有效能數據**。
（除錯初期就是因為這個誤判了一次元凶。）

```js
g.ui.startScreen.classList.add('hidden');
g.start();
```

### 坑 3：headless 是軟體光柵化

`render` 會吃掉大部分幀時間，**絕對值不能代表真機**，只能做 A/B 相對比較。
測試機是 Mac mini M4，GPU 合成太快，用 fps 當指標會量到「一切正常」再把問題退回手機。

### 坑 4：效能面板每 250 ms 才寫一次 DOM

面板文字會落後實際值。要精確數字請**直接讀遊戲物件**（`game.enemies.length` 等），
不要從面板文字反推。

### 坑 5：彈窗會停掉 update

測量期間若跳出升級卡，`update()` 不會執行，數據就斷了。測效能時先關掉：

```js
g.triggerLevelUp = () => {};
```

### E4b 例外狀態跨局清除
1. 開一局，console 注入 3 次例外讓紅色告示跳出
2. 不重整頁面，直接開新局

> **B11 的驗收指標已更換（Lane E v3 指出前一版不可用）。**
>
> 舊指標「凍結% > 15%」是錯的：面板每 250ms 重寫一次，一次 0.035 秒的頓格在 10fps
> 下就吃掉整整一幀 = 33–50%，即使 60fps 也要 2–3 幀 = 13–20%。**這個門檻連一次
> 孤立的頓格都擋不住**，跟有沒有洗版無關。而且 `頓格n` 數的是**幀數不是事件數**，
> 一次 0.08 秒的 Boss 頓格在低幀率下會顯示成「頓格5」，看起來像五次精英頓格。
>
> 面板已改為同時顯示兩者，並新增與幀率無關的指標：
> ```
> 凍結 0%  (頓格3幀/1次 暫停0)
> 頓格最小間隔 1.73s  hs 0.00
> ```
> **新驗收條件**：`頓格最小間隔 ≥ 0.5s`（`—` 表示整局未觸發或只觸發過一次）。
> 事件數與最小間隔是整局累計，開新局才歸零。
>
> 本機 A/B（同腳本同負載）：節流 ON → 2 次、最小間隔 2.000s；
> 節流 OFF → 17 次、最小間隔 0.033s（每個邏輯步都觸發）。

## 5. Lane C — 效能量測

> **不要用 fps 當指標**（理由見坑 3）。改量工作量：每幀送出多少繪圖指令、
> 塗了多少像素、配置了多少物件。這些數字在任何機器上跑都一樣。

### C1 跑探針

```bash
npx http-server -p 8899 -s
node tools/perf-probe.mjs
```

探針做了三件事讓結果可重現：強制軟體光柵化（快機器也會暴露填充率瓶頸）、
固定 120 幀固定 dt（不用 rAF，消除 vsync 雜訊）、固定亂數種子（場面一致）。

### C2 基準對照

本機 2026-09-10 量測：

| 情境 | 每幀繪圖指令 | 每幀色彩字串 | 每幀塗抹倍率 | 其中加色混合 | renderMs |
|---|---|---|---|---|---|
| 空場基準 | 68 | 9 | 10.25× | 0 | 0.4 |
| 滿場敵人（無狀態特效） | 572 | 16 | 12.38× | 0 | 18.5 |
| 滿場灼燒 | 1773 | 16 | 13.69× | 1.31× | 28.9 |
| 灼燒 + 中毒 5 層 | 4172 | 494 | 14.89× | 2.51× | 44.0 |

**「塗抹倍率」= 每幀塗抹像素 ÷ 螢幕像素。** 10× 表示每個像素平均被畫了 10 次。

**回報**：在 M4 上跑同一份探針，整張表貼回來。

- **前四欄應與上表幾乎相同** —— 差超過 5% 表示程式碼或場景生成有變，先查清楚
- **renderMs 會小很多**（M4 較快），這正常，**但四個情境之間的比例應該吻合**

### C3 判定門檻

| 指標 | 現況 | 判定 |
|---|---|---|
| 加色混合塗抹倍率 | 2.51× | > 2 是手機上的主要風險 |
| 每幀繪圖指令 | 4172 | > 3000 偏高 |
| 每幀色彩字串 | 494 | 每個都要解析色彩，> 200 值得查來源 |
| renderMs / updateMs | 44 / 0.6 | 瓶頸在繪圖不在邏輯 |

### C4 改動前後怎麼比

```bash
node tools/perf-probe.mjs --json > before.json
# ...改程式...
node tools/perf-probe.mjs --json > after.json
diff <(jq -S . before.json) <(jq -S . after.json)
```

一次只改一個變因，兩次都在同一台機器上跑。**只回報差多少，絕對值跨機器沒有意義。**

### C5 狀態特效外觀確認（回歸清單第 10 項）

灼燒/中毒特效已改為烘焙 sprite。**外觀應該完全沒變。**
對照修正前後的截圖，確認橘紅火光與綠色氣泡的顏色、大小、明滅節奏一致。
**失敗**：任何肉眼可見的差異都要回報並附截圖。

### C6 真機交叉驗證（**只有這項需要手機**）

探針是模擬（強制軟體光柵化），而手機是 GPU 合成，兩者對「加色大面積填充」的
敏感度不一定相同。在手機上帶**火焰/毒**系武器打一局、再帶**不含火毒**的打一局，
同關卡、同時間點，各記錄 `?perf=1` 面板。

**通過**：兩局 `幀` 中位數差距不大 → 狀態特效不是真機主因，要改查別處
**失敗（= 確認問題）**：帶火毒明顯更卡 → 回報兩組面板原文

> 已知槓桿：縮小光暈半徑 1.5→1.0，本機 21.2 → 23.6 fps，效果有限且會改外觀。
> **C6 有結論前不要動。**

## 7. Lane E — 模式、耐久、跨局重置

> **本 Lane 的定位**：保證「計數沒有洩漏」+「render ms 沒有成長」。
> **不負責後期卡頓的判斷** —— headless 的「幀」欄被夾具汙染（坑 1），
> 卡頓判斷走 Lane C 探針或真機。

### E1 三模式各打一局到結束
生存者 / 守塔 / 每日挑戰。各記錄：戰死或通關、有無錯誤告示、最卡時的面板。

> **模式**只有 `survivor` 與 `defense` 兩種（`js/modes.js`），都以擊敗終極首領為終點。
> 但**關卡**另有 `endless`「深淵無盡戰」（`js/levels.js:201`）：無限波次、Boss 每 90 秒
> 輪播、`config.js:813` 有「存活 10 分鐘」成就。**耐久測試應該用它**，
> 不需要再靠釘住首領血量。

### E1b 無盡關卡
`endless` 的波次公式與其他關卡不同（`Spawner.js:61`）：
`interval = max(0.15, 0.55 - t×0.00055)`、`batch = 1 + min(5, floor(t/150))`
→ 10 分鐘時約 22.7 隻/秒，**這才是 `MAX_ENEMIES = 250` 這個預算的設計對象**。

打一局 `endless` 到 10 分鐘以上，記錄 `敵` 是否逼近 250、以及各項計數與 `render ms`。
這同時是 Lane C 的極端場景參考。

### E2 10 分鐘耐久（優先用 `endless` 關卡，其次守塔）
每 2 分鐘記錄一次面板。重點看**是否單調惡化**：

- `粒子` 是否停在上限 900 不下降
- `殘跡` `掉落` `投射` 是否只增不減
- `render ms` 是否隨時間單調變差

**失敗**：任一計數只增不減 → 回報是哪一欄與各時間點數值

> 上一輪結論：無洩漏。`掉落` 在 8:00 到 362 後掉回 146，證明 60 秒過期有效；
> 4:00 掉到 2 是擊殺里程碑的磁力空投清場。**本輪應重現這個型態。**

### E3 磁鐵 × 滿場敵人 × 口袋滿（原始 bug 完整重現）
守塔打到 5 分鐘，口袋塞滿道具（含 `manna_prism`），在敵人最多時吃磁鐵。
**通過**：不凍結、無錯誤告示、`掉落` 正常歸零

### E4 跨局狀態重置（**本輪新增**）

單局拉長測不到跨局的重置問題。**連續打 5 局不重新整理頁面**（戰死就重開一局），
每局結束時記錄：

| 檢查項 | 通過條件 |
|---|---|
| `敵` `投射` `掉落` `粒子` `殘跡` `砲塔` `傭兵` | 新局開始時應歸零 |
| `待升級` | 新局開始時應為 0 |
| `frameErrorCount` | 不應跨局累積增長 |
| `狀態` | 每局開始都是 `PLAYING` |
| 第 5 局的 `render ms` | 與第 1 局相當（不應變差） |

**失敗**：任何計數帶到下一局 → 回報是哪一欄、第幾局、數值

> `start()` 裡有三處計數歸零（`js/main.js` 的 63/884/1028 附近）。
> 跨局殘留是這類程式最典型的洩漏來源，單局測試完全看不到。

## 8. 自動化夾具

Lane C 直接用 `tools/perf-probe.mjs`，煙霧測試用 `tools/smoke-branches.mjs`，
**不要自己重寫**。

```bash
node tools/perf-probe.mjs                    # 全部情境
node tools/perf-probe.mjs --scenario=burn5   # 單一情境
node tools/perf-probe.mjs --json             # 供 diff
node tools/smoke-branches.mjs                # 51 個罕見分支
```

環境變數：`PROBE_URL`、`CHROMIUM`、`PW_MODULE`（playwright 未裝在專案內時指向絕對路徑）。

其餘 Lane 自己寫腳本時用這份骨架（已實測：120 秒遊戲時間約 13 秒跑完、0 例外、無穿隧）：

> **注意**：腳本裡的玩家不會移動，所以幾乎不撿水晶、等級偏低、很快就戰死，
> 這是正常的。要測到後期內容得自己補移動邏輯或直接灌敵人/道具。

```js
const pw = (await import(process.env.PW_MODULE || 'playwright')).default;
const b = await pw.chromium.launch({ executablePath: process.env.CHROMIUM });
const ctx = await b.newContext({ viewport:{width:390,height:844}, deviceScaleFactor:2, isMobile:true });
const p = await ctx.newPage();
p.on('pageerror', e => console.log('PAGEERR', e.message));
await p.goto('http://127.0.0.1:8899/index.html?perf=1');
await p.waitForFunction(() => window.game);

await p.evaluate(async () => {
  const g = window.game;
  g.ui.startScreen.classList.add('hidden');   // 坑 2
  g.start();
  for (let i = 0; i < 40 && !g.enemies.length; i++) await new Promise(r => setTimeout(r, 200));
  g.triggerLevelUp = () => {};                 // 坑 5（只在測效能時）
});

// 固定步進推進遊戲時間（坑 1）。實測：120 秒遊戲時間約 13 秒實時跑完，無穿隧。
await p.evaluate(async ({ seconds }) => {
  const g = window.game, SUB = 1 / 30;
  for (let t = 0; t < seconds / SUB; t++) {
    if (g.state !== 'PLAYING') break;   // 玩家不動會戰死，別再空轉
    g.update(SUB);
    if (t % 4 === 0) g.render();
  }
}, { seconds: 120 });

// 讀計數請直接讀遊戲物件（坑 4）
await p.evaluate(() => ({
  敵: game.enemies.length, 掉落: game.dropItems.length,
  粒子: game.particles.particles.length, 例外: game.frameErrorCount || 0,
  錯誤: game.frameError?.message || null, 狀態: game.state,
}));
```
