# gaga-survivor 測試計畫（Hermes 多開平行測試）

**目標**：驗證近期修正是否成立，並把「後期卡頓」的成因從推測收斂為數據。

**設計原則**：五條 Lane 互相獨立，可同時開五個 agent，彼此不需等待、不共用狀態。
每個項目都有明確的通過條件與失敗回報格式，不接受「感覺順暢」這種結論。

---

## 0. 共同前置（每個 agent 開工前都要做一次）

### 0.1 確認拿到的是新版

GitHub Pages 有快取，**用無痕視窗**開，或在 DevTools 勾 Disable cache。

```
https://cormort.github.io/gaga-survivor/?perf=1
```

版本確認：左上效能面板必須有 **6 行以上**，且第 3 行是 `凍結 x% (頓格n 暫停n) hs x.xx`。
只有 6 行、沒有「凍結」那行 = 舊版，快取沒清掉，**先解決這個再測**。

本機測試改用：

```bash
npx http-server -p 8899 -s     # 專案根目錄
# → http://127.0.0.1:8899/index.html?perf=1
```

### 0.2 效能面板欄位

```
60 fps   幀 16.7 / 最差 25 ms          ← 幀時間中位數與該窗期最差幀
update 0.20  render 0.44 ms  跑16幀    ← JS 耗時；「跑N幀」是實際完成的更新幀數
凍結 0%  (頓格0 暫停0)  hs 0.00        ← 世界沒有前進的幀數佔比
敵 17  投射 8  敵彈 0
掉落 32  粒子 286  殘跡 5
砲塔 9  傭兵 1  待升級 0
狀態 PLAYING
✖ 每幀例外 ×N                          ← 只有出事才會出現
<錯誤訊息>
<拋出位置>
```

### 0.3 判讀規則（重要，避免又誤判）

| 面板徵狀 | 結論 | 該回報什麼 |
|---|---|---|
| `update/render 0.00` + `跑0幀` + 狀態 PLAYING | **例外凍結**，不是效能問題 | 面板最下方三行（錯誤訊息與位置） |
| `跑N幀` 正常但 `幀` 數字很大 | 真的效能不足 | 完整面板 + 當下敵/投射/粒子數 |
| `凍結 x%` 的「暫停」不為 0 | 狀態機卡在彈窗 | 當時的 `狀態` 欄位值 |
| `凍結 x%` 的「頓格」不為 0 | 打擊頓格 | `hs` 欄位的數值 |

**`fps` 這個數字本身沒有意義**，一定要搭配 `跑N幀` 一起看：畫面凍結時 fps 照樣是 60。

## 2. Lane A — 磁鐵與掉落物

> 對應修正：掉落物穿透玩家、60 秒存活時間、升級卡批次化

### A1 磁鐵不留殘留物
1. 進入遊戲，打到場上有 30 顆以上經驗水晶（面板 `掉落` 欄確認）
2. 吃磁鐵（或撿到 🧲）
3. 觀察面板 `掉落` 欄

**通過**：`掉落` 在 2 秒內降到接近 0（剩下的只能是裝備/寶箱這類不會被吸的）
**失敗**：`掉落` 停在某個數字不再下降 → 有水晶穿過玩家撿不到，回報停在多少

### A2 低幀率下的磁鐵
同 A1，但先讓場上敵人超過 150 隻（面板 `敵` 欄）再吃磁鐵。
**通過條件同 A1**。這是原始 bug 的重現條件，幀率越低越容易失敗。

### A3 掉落物過期
1. 讓場上累積 20 顆以上水晶，然後**遠離**它們
2. 等 60 秒

**通過**：水晶在最後 5 秒閃爍後消失，`掉落` 欄下降
**失敗**：不消失，或裝備/寶箱也跟著消失（那些不該過期）

### A4 升級卡不再連環閃爍
1. 累積大量水晶後吃磁鐵，讓它一次升好幾級
2. 錄影或仔細觀察卡片之間

**通過**：卡片連續出現，中間**不會**閃回遊戲畫面
**失敗**：每張卡之間畫面閃一下 → 回報閃了幾次

### A5 升級卡數量正確
承 A4，記錄升級前後的 `LV` 差值與實際選了幾張卡。
**通過**：張數 == 升的級數
**失敗**：張數 < 級數 → 回報兩個數字

## 3. Lane B — 消耗品

> 對應修正：曼納稜晶 `cooldowns.clear()` 必炸

九種：`potion` `elixir` `atk_potion` `shield_potion` `luck_potion` `stopwatch` `holy_water` `manna_prism` `magic_ticket`

**每一種都要走兩條路徑**：

- **路徑 1（口袋使用）**：口袋是空的 → 撿起來 → 按 `E` 使用
- **路徑 2（即拾即用）**：口袋先塞滿**不同**道具（例如藥水 ×2）→ 再撿這一種 → 會直接觸發

> 路徑 2 是原始 bug 的觸發條件，**不可跳過**。磁鐵會一次灌進大量道具、口袋必定塞滿，
> 所以實戰中一定會走到這條。

**通過**：兩條路徑都不出現紅色錯誤告示，面板無 `✖ 每幀例外`，遊戲繼續運作
**失敗**：回報是哪一種道具、哪一條路徑、面板最下方的錯誤訊息全文

### B10 曼納稜晶效果驗證
使用前先把武器打到冷卻中（連續開火），使用後確認武器立刻可以再開火、衝刺也回滿。
**通過**：兩者都歸零（這半邊效果先前從未生效過，是這次一併修的）

## 4. Lane C — 效能量測

> **不要用 fps 當指標。** 測試機是 Mac mini M4，GPU 合成太快，後期卡頓在那台機器上
> 壓不出來；量到「一切正常」只會把問題原封不動退回給手機。fps 還同時受 vsync、
> 機器負載、瀏覽器排程影響，跨機器根本不可比。
>
> 改量**工作量**：每幀送出多少繪圖指令、塗了多少像素、配置了多少物件。
> 這些數字在任何機器上跑都一樣。

### C1 跑探針

```bash
npx http-server -p 8899 -s          # 終端機 A，專案根目錄
node tools/perf-probe.mjs           # 終端機 B
```

探針做了三件事讓結果可重現：

1. **強制軟體光柵化**（`--use-gl=swiftshader`）—— 快機器也會暴露填充率瓶頸
2. **固定步進**（120 幀、固定 dt，不用 rAF）—— 消除 vsync 與排程雜訊
3. **固定亂數種子** —— 每次跑的場面一致

### C2 目前基準（本機 2026-09-10 量測）

| 情境 | 每幀繪圖指令 | 每幀色彩字串 | 每幀塗抹倍率 | 其中加色混合 | renderMs |
|---|---|---|---|---|---|
| 空場基準 | 68 | 9 | 10.25× | 0 | 0.4 |
| 滿場敵人（無狀態特效） | 572 | 16 | 12.38× | 0 | 18.5 |
| 滿場灼燒 | 1773 | 16 | 13.69× | 1.31× | 28.9 |
| 灼燒 + 中毒 5 層 | 4172 | 494 | 14.89× | 2.51× | 44.0 |

**「塗抹倍率」= 每幀塗抹的像素 ÷ 螢幕像素。** 10× 表示每個像素平均被畫了 10 次。

**要回報的**：在 M4 上跑同一份探針，把整張表貼回來。

- **前四欄（指令數、字串數、塗抹倍率、加色混合）應該與上表幾乎相同** —— 若差超過 5%，
  表示程式碼或場景生成邏輯有變，先查清楚再往下
- **renderMs 會小很多**（M4 比較快），這正常，**但四個情境之間的比例應該吻合**

### C3 判定門檻

| 指標 | 現況 | 判定 |
|---|---|---|
| 加色混合塗抹倍率 | 2.51× | > 2 就是手機上的主要風險 |
| 每幀繪圖指令 | 4172 | > 3000 偏高 |
| 每幀色彩字串 | 494 | 每個都要解析色彩，> 200 值得查來源 |
| renderMs / updateMs | 44 / 0.6 | 瓶頸在繪圖，不在遊戲邏輯 |

### C4 改動前後怎麼比

```bash
node tools/perf-probe.mjs --json > before.json
# ...改程式...
node tools/perf-probe.mjs --json > after.json
diff <(jq -S . before.json) <(jq -S . after.json)
```

**規則**：一次只改一個變因，兩次都在同一台機器上跑。
只回報「差多少」，不要回報絕對值 —— 絕對值跨機器沒有意義。

### C5 真機交叉驗證（只有這項需要手機）

探針是模擬，最終仍需要一次真機對照。在手機上帶**火焰/毒**系武器打一局、
再帶**不含火毒**的打一局，同關卡、同時間點，各記錄 `?perf=1` 面板。

**通過**：兩局的 `幀` 中位數差距不大 → 狀態特效不是真機主因，探針的結論不適用，要改查別處
**失敗（= 確認問題）**：帶火毒明顯更卡 → 回報兩組面板原文

> 這一項的結論決定要不要動視覺效果。已知槓桿：縮小光暈半徑 1.5→1.0，
> 本機 21.2 → 23.6 fps，效果有限且會改外觀。**在 C5 有結論前不要動。**

## 5. Lane D — 例外處理與狀態機

### D1 錯誤告示會出現
DevTools console 執行：
```js
game.updateHazards = function(){ throw new Error('測試用'); };
```
**通過**：約 0.5 秒後畫面底部跳出紅色告示，含訊息與「重新載入」按鈕
**失敗**：沒跳、或整個頁面卡死（連告示都畫不出來）

### D2 偶發例外不打擾
```js
(function(){ const f = game.updateHazards; let n = 0;
  game.updateHazards = function(...a){ if (n++ < 3) throw new Error('偶發'); return f.apply(this, a); }; })();
```
**通過**：不跳告示，遊戲照常進行

### D3 彈窗狀態機
逐一開關：升級卡、寶箱、商人、祝福、裝備、暫停。每次關閉後檢查面板 `狀態` 是否回到 `PLAYING`。
**失敗**：卡在某個狀態 → 回報是哪一個彈窗、`狀態` 欄顯示什麼

### D4 彈窗期間的畫面
彈窗開著時畫面是靜止的（這是刻意設計，不是 bug）。
**要確認的是**：關閉後畫面立刻恢復更新，`跑N幀` 回到正常值。

## 6. Lane E — 模式與耐久

### E1 三種模式各打一局到結束
生存者 / 守塔 / 每日挑戰。各記錄：是否完整通關或戰死、有無錯誤告示、最卡時的面板。

### E2 長時間耐久（守塔模式，至少 10 分鐘）
每 2 分鐘記錄一次面板。重點看**是否單調惡化**：

- `粒子` 是否停在上限 900 不下降
- `殘跡` `掉落` `投射` 是否只增不減
- `幀` 中位數是否隨時間單調變差

**失敗**：任一計數只增不減 → 有洩漏，回報是哪一欄與各時間點的數值

### E3 磁鐵 × 滿場敵人 × 口袋滿（原始 bug 的完整重現）
守塔模式打到 5 分鐘後，口袋塞滿道具，在敵人最多時吃磁鐵。
**通過**：不凍結、無錯誤告示、`掉落` 正常歸零

## 7. 自動化夾具

**Lane C 直接用 `tools/perf-probe.mjs`，不要自己重寫。**

```bash
node tools/perf-probe.mjs                    # 全部情境
node tools/perf-probe.mjs --scenario=burn5   # 單一情境
node tools/perf-probe.mjs --json             # 供 diff 比對
```

環境變數：`PROBE_URL`（預設 127.0.0.1:8899）、`CHROMIUM`（自訂 Chromium 路徑）、
`PW_MODULE`（playwright 未裝在專案內時指向絕對路徑）。

其餘 Lane 要自己寫腳本時，用下面這份骨架（已驗證可用）：

已驗證可用。需要 `playwright`，Chromium 在 `/opt/pw-browsers/chromium`。

```js
import pw from 'playwright';
const b = await pw.chromium.launch();
const ctx = await b.newContext({ viewport:{width:390,height:844}, deviceScaleFactor:2, isMobile:true });
const p = await ctx.newPage();
p.on('pageerror', e => console.log('PAGEERR', e.message));
// 模擬手機 CPU
await (await ctx.newCDPSession(p)).send('Emulation.setCPUThrottlingRate', { rate: 4 });
await p.goto('http://127.0.0.1:8899/index.html?perf=1');
await p.waitForFunction(() => window.game);

await p.evaluate(async () => {
  const g = window.game;
  g.ui.startScreen.classList.add('hidden');   // 照真實流程隱藏，否則會留一層全螢幕 blur 汙染量測
  g.start();
  for (let i = 0; i < 40 && !g.enemies.length; i++) await new Promise(r => setTimeout(r, 200));
});

// 造大量敵人
await p.evaluate(() => {
  const g = window.game, proto = g.enemies[0];
  for (let i = 0; i < 300; i++) {
    const e = Object.create(Object.getPrototypeOf(proto));
    Object.assign(e, proto);
    e.x = g.player.x + (Math.random() - 0.5) * 1200;
    e.y = g.player.y + (Math.random() - 0.5) * 1200;
    e.isDead = false; e.hp = 1e9; e.maxHp = 1e9;
    g.enemies.push(e);
  }
});

// 讀面板 / 讀例外
await p.evaluate(() => window.game.perf.el.textContent);
await p.evaluate(() => ({ n: window.game.frameErrorCount || 0, msg: window.game.frameError?.message }));
```

**踩過的坑，別重蹈**：
- 不隱藏 `#start-screen` 就 `g.start()` → 會留一層 1280×720 的 `backdrop-filter: blur`，讓所有效能數據失真
- headless 是**軟體光柵化**，`render` 會吃掉大部分幀時間，**絕對值不能拿來代表真機**，只能做 A/B 相對比較
- 要量 A/B 一定要**同一份腳本只改一個變因**，否則結論不可信

## 8. 回報格式

每個 Lane 回一份，格式統一：

```
Lane: C
環境: Pixel 8 / Chrome 141 / 無痕
版本: 面板有「凍結」行 = 新版

| 項目 | 結果 | 證據 |
|------|------|------|
| C1 05:00 | 記錄完成 | <完整面板文字> |
| C2 火毒局 | 中位 38ms | <面板> |
| C2 無火毒局 | 中位 21ms | <面板> |

結論: <一句話>
待決策: <需要我判斷的取捨>
```

**回報原則**：面板文字請**原文照貼**，不要摘要。先前就是因為只看到部分數字而誤判了兩次
（`backdrop-filter` 一次、打擊頓格一次），都是被不完整的資訊帶偏的。
