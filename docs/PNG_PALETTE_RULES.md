# 壓色規則（PNG → 256 色調色盤）

> 適用對象：`assets/` 下的所有 PNG。工具：`tools/optimize_pngs.py`。
> 這份文件是**規則**，不是建議 —— 壓色是有損轉換，違反下面的守門條件就會出現肉眼可見的破壞。

---

## 為什麼要壓

- `assets/` 的 PNG 是整個 repo 的體積主體；`sw.js` 的 `PRECACHE` 會把它們全部塞進 PWA 預快取，
  **玩家第一次開啟就要下載**（這一輪實測：294 檔 / 37.7 MB，其中 31.6 MB 進預快取）。
- **無損重壓沒有用**：用 Pillow `optimize=True, compress_level=9` 重壓前 40 大 PNG，實測只省 **0.2%**
  —— 這些圖本來就壓得很乾。唯一有效的手段是降到 256 色調色盤（實測省 78–86%）。
- 所以問題不是「要不要壓」，而是「**壓到什麼程度還看不出來**」。

## 三條規則（缺一不可）

### 1. 範圍：只碰 `assets/**/*.png`

- **不碰 `icons/`**：PWA 圖示依規範必須**完全不透明**（maskable 尤其），`tools/verify-pwa.mjs` 會把關
  （不得有 alpha 通道或 `tRNS`），而且圖示總量要 < 200 KB。要處理圖示請用 `tools/flatten-icons.py`。
- **不碰 `tools/`**：`tools/xian_source_sheet.png` 這類是**切割 sprite 的來源圖**，壓了會讓之後重切出來的
  素材品質下降（來源圖不進遊戲、不佔玩家下載）。
- 已經在預快取之外、玩家不會下載的東西，不必動。

### 2. 品質守門：**可見差** ≤ 4/255 才肯轉

守門用的不是「RGBA 直接比」，而是**預乘 alpha 後**的平均差（`stats()` 實作），並把 alpha 本身的變化
一起算，取兩者較大者為「可見差」。`tools/optimize_pngs.py` 預設 `--max-mean 4.0`；超過就把原檔留著。

**為什麼一定要預乘**：AI 產圖常常在 `alpha = 0`（完全透明）的區域留下棋盤格或雜色 RGB ——
那是**看不到的像素**。直接比 RGBA 會把它們算進平均值，把好素材誤判成「不能壓」。
實測同一批 287 張素材：

| 指標 | 判定可以轉 | 被擋下 | 擋下的體積 |
|---|---|---|---|
| RGBA 直接比 | 177 張 / 省 18.6 MB | 84 張 | 7.04 MB（**誤殺**：`zodiac/*`、`bullets/*`、`weapons/*` 的發光類） |
| **預乘 alpha（可見差）** | **258 張 / 省 23.9 MB** | **3 張** | 0.46 MB |

誤殺的那批（`zodiac/dragon_evil` 直接比 79.7、`tiger_hero` 64.2）改用可見差後只剩 2–4，
1:1 疊在棋盤底上目視也確實看不出差異 —— 它們的「巨大差異」全部來自透明區域。

門檻訂 4 的理由：正常轉換的可見差落在 **1.6–4.0**（1:1 目視看不出來），而唯一會被擋下的
是逼近門檻的少數（這一輪 3 張：`boss_swamp` 4.49、`td/arcane_storm` 4.28、`weapons/guardian` 4.09）。
**不要為了省幾百 KB 去調高門檻**；真的要處理那幾張，該換的是格式（見下），不是硬壓。

### 3. 每次壓色都要發版

`version.json` 的 `version` 與 `sw.js` 的 `FALLBACK_VERSION` 必須同步遞增。
Service Worker 的快取名稱由版號決定，且非預快取資源走「快取優先 + 背景更新」——
**不換版，已安裝的 PWA 就會繼續吃舊的 runtime 快取圖**，使用者看到的是「改了但沒變」。
（`tools/verify-pwa.mjs` 會比對這兩處。）

## 標準流程

```bash
# 1) 先看會動哪些、省多少、哪些被守門擋下（預設就是 dry-run，不會改檔）
python3 tools/optimize_pngs.py --dry-run --csv /tmp/pngs.csv

# 2) 產生 1:1 對照圖，人眼看過再動手（左原圖／右 256 色，都疊在棋盤底上）
python3 tools/optimize_pngs.py --compare assets/zodiac/tiger_hero.png

# 3) 套用
python3 tools/optimize_pngs.py --apply

# 4) 更新下載大小、檢查 PWA 沒被動到
node tools/audit-assets.mjs --write-version
node tools/verify-pwa.mjs

# 5) 發版（version.json + sw.js FALLBACK_VERSION），然後驗線上真的換了
```

驗收清單（缺一不可）：

- [ ] 每張都**尺寸不變、可解碼**（工具內建斷言，`--apply` 前就會擋）
- [ ] 1:1 對照圖看過（**要疊在同一個棋盤底／真實地表貼圖上看 alpha 邊緣**，單看一張圖看不出白邊／硬邊）
- [ ] `node tools/audit-assets.mjs`：無死檔、預快取無缺口、`assetsKB` 沒過期
- [ ] 遊戲真的載得到：以 playwright 走真實載入路徑（`Ground.getGroundTexture()`、貼圖表），
      確認載入旗標為 true、`naturalWidth` 正確、`pageerror` 為 0
- [ ] 線上換版後 `curl` 那個檔案確認 **Content-Length 真的變小**（只驗版號不算數）

## 這一輪的實測數據（2026-10）

以 v105 的 main（含新繪的守塔路徑貼圖與仙山裝飾）為基底重跑：

| 範圍 | 原大小 | 壓後 | 降幅 | 狀態 |
|---|---|---|---|---|
| `assets/ground/*.png`（16 張，進關才下載） | 31.4 MB | 6.3 MB | **-80%** | 已進 main（v103） |
| 全部 `assets/**/*.png`（287 張） | 39.9 MB | 14.7 MB | **-63%** | 258 張改動、省 24.0 MB（v106） |
| 被守門擋下（可見差 > 4） | 0.46 MB | — | — | 3 張，保留原檔 |
| 重壓沒變小（本來就是調色盤／已壓過） | 5.8 MB | — | — | 26 張（含已轉的 16 張 ground） |
| 無損重壓（對照組） | — | — | **-0.2%** | 確認此路不通 |

整體效果：`assets/` 38 MB → 14.4 MB（若從壓色前的原始素材算起是 **61.6 MB → 14.4 MB**），
PWA 預快取（玩家第一次開啟的下載量）**31.6 MB → 8.3 MB**，`version.json` 的 `assetsKB` 32250 → 8273。

解析度與模式：貼圖維持原尺寸（地表 1024×1024）；輸出為 8-bit 調色盤 PNG（有 alpha 的會帶 `tRNS`）。

## 為什麼不用 WebP

WebP（尤其 lossy）對「發光／半透明漸層」這類素材的壓縮效率比調色盤 PNG 更好，是那幾張被守門擋下素材的正解。
但目前**所有素材 URL 都是 `.png`**，改成 WebP 要動載入端（`js/sprites.js`、`Ground.js`、預快取清單、
`audit-assets.mjs`），canvas 相容性與離線快取也要重新驗一輪 —— 屬於獨立的一次改動，
不跟調色盤壓色混在一起做。要做就單獨開一輪，並沿用同一套「先量測、再對照圖、後發版」的流程。

## 踩過的坑

- **透明區域的 RGB 是陷阱**（本輪最大的坑）：`alpha=0` 的像素裡可能存著棋盤格或雜色，
  直接比 RGBA 會把它們算進誤差，把好素材誤判成不能壓（本輪誤殺 84 張 / 7.04 MB）。
  一律用**預乘 alpha 的可見差**當守門指標，並用 `--compare` 疊棋盤底目視複驗。
- **alpha 邊緣才是真風險**：量化後 alpha 也只保留 256 階，sprite 羽化邊可能出現硬邊或白邊。
  對照圖要疊在**棋盤底或真實地表貼圖**上看 1:1，不要只看單張圖或縮圖。
- **不要用最大可見差當唯一守門**：單一極端像素很容易差到 255（漸層量化必然發生），
  平均值才反映整體保真度；`--max-delta` 預設關閉。
- **已轉過的檔案會回報「重壓沒變小」**：那是 idempotent，不是失敗。
- **這是不可逆的品質取捨**：後悔就 `git revert` 該 commit，或用 `--colors 128/256` 重跑。
