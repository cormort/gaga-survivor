# 🦆 呱呱特工 (Gaga Survivor)

一款類似《噠噠特攻 / 呱呱特工》（Survivor.io / 吸血鬼倖存者）風格的 2D 俯視角 Roguelike 割草動作網頁遊戲。**兩種作戰模式**：純走位割草的「生存者」，與要守住基地核心的「守塔」。挑選特工出擊，選一張關卡，在怪物狂潮中走位突圍、佈署砲塔、升級裝備，合成震撼全場的毀滅級超武。單局 8 分鐘，擊敗終極首領即通關並解鎖下一關。

**▶️ 線上遊玩：<https://cormort.github.io/gaga-survivor/>**（電腦與手機皆可）

---

## 🚀 本機執行

因為使用 ES Modules，必須透過 HTTP 伺服器開啟（直接雙擊 `index.html` 會被瀏覽器的 CORS 政策擋下）：

```bash
python3 -m http.server 8791
```

然後開啟 <http://localhost:8791/index.html>。

## 📲 安裝成 App（PWA）

線上版可直接「安裝」到桌面／主畫面，之後**離線也能玩**（第一次載入後全部資源進快取）。

- **Android / Chrome**：網址列右側的安裝圖示，或選單「安裝應用程式」；遊戲內偵測到可安裝時，HUD 下方會出現「安裝成 App」橫幅並帶一顆「安裝」按鈕（真的攔到 `beforeinstallprompt` 才給按鈕）。
- **iOS / Safari**：分享選單 → 「加入主畫面」。iOS 不會觸發安裝提示，所以橫幅給的是操作步驟、不給按鈕（按了沒反應比不給更糟）。
- **iOS 上的非 Safari 瀏覽器（Chrome/Edge/Firefox）與 App 內建瀏覽器（LINE / Messenger / IG…）**：這些環境**完全無法**加入主畫面（iOS 只有 Safari 做得到；App 內建瀏覽器沒有任何安裝途徑）。橫幅會直接講明要改用 Safari／用瀏覽器開啟，而不是安靜地什麼都不給。
- **常駐入口**：「🏠 養成基地」裡的「📲 安裝成 App」隨時可以再叫出安裝說明（已安裝成 App 時自動隱藏）。自動橫幅每個工作階段最多跳一次，關掉也不會從此找不到入口。
- **離線**：`js/pwa.js` 註冊 `sw.js`，安裝時預cache 253 項（`./`、`index.html`、`css/style.css`、`manifest.webmanifest`、`version.json`、6 個圖示、**全部 47 個 JS 模組**、196 個美術素材，約 40 MB）。抓取策略是**快取優先 + 背景重新驗證**（同源 GET 才攔截，跨網域完全不碰），失敗時導覽回快取外殼、其他資源回 503。
- **更新**：偵測到新版 Service Worker 時，HUD 下方出現「有新版本可用／重新載入」，點下去送 `SKIP_WAITING` 並在 `controllerchange` 後重載；舊版快取在 activate 時清除。
- **限制**：Service Worker 只在 HTTPS 或 `localhost` 生效；用區網 IP 以 HTTP 開啟時註冊會靜默失敗（遊戲照常運行，只是沒有離線與安裝）。
- 檔案：`manifest.webmanifest`、`sw.js`、`js/pwa.js`、`icons/`（SVG 原稿 + 192/512/maskable-512/apple-touch-180）。

> **圖示必須完全不透明**。`tools/flatten-icons.py` 會把重繪後的圖示壓平成不透明的調色盤 PNG
> （合成到 manifest 的 `background_color`），`python3 tools/flatten-icons.py --check` 可單獨檢查。
> `verify-pwa.mjs` 也會把關：圖示不得有 alpha 通道或 `tRNS`。
> 理由：maskable 圖示依規範**必須 opaque**（MDN：give your maskable icon an opaque background
> color to fill the entire icon area），而透明的 `purpose: any` 圖示在 Android 會被塞進白色圓圈。
> 用 AI 工具重繪圖示時很容易產出「透明圓角 + 羽化邊」，改完務必跑一次 `--check`。
- 回歸測試：`node tools/verify-pwa.mjs`（71 項，含「Chrome 可安裝性」CDP 判定、圖示必須完全不透明、各手機環境的安裝指引矩陣、安裝失敗後的「建立捷徑」備援、關掉伺服器後的離線啟動）、`node tools/verify-pwa-update.mjs`（v1→v2 更新流程）、`node tools/bannerbox.mjs`（三種螢幕尺寸的橫幅版面）。

> **可安裝性要怎麼驗才準**：光看 manifest/圖示/SW 的靜態檢查驗不出「Chrome 願不願意給安裝」。
> `Playwright` 的 `browser.newContext()` 是無痕情境，`Page.getInstallabilityErrors` 只會回
> `in-incognito`，真正的問題會被同一個錯誤蓋掉；而且**不指定 `executablePath` 時回傳的永遠是空陣列**
> （連沒有 manifest 的頁面都不會被判失敗）。`verify-pwa.mjs` 因此改用持久化 profile（非無痕）
> ＋明確指定執行檔，並先跑一次「無 manifest 頁面必須被判 `no-manifest`」的控制組自我檢查。


> 若日後新增 `js/**` 模組，記得同步加進 `sw.js` 的 precache 清單，否則首次離線載入會少一支。
> 檢查指令：`comm -23 <(find js -name '*.js' | sed 's|^|./|' | sort) <(grep -o "'\./js/[^']*'" sw.js | tr -d "'" | sort -u)`

## 🎮 操作方式

- **電腦操作**：
  - `W` `A` `S` `D` 或 `方向鍵`：特工移動
  - `Space`（空白鍵）：**戰術閃避翻滾 (Dash)**（0.22 秒高速突進 + 無敵幀護盾，3.8 秒冷卻）
  - `E` / `F` 鍵、HUD 🎒 兩格口袋、動作欄兩顆 🎒 按鈕：**使用第 1 / 第 2 格戰術口袋道具**
  - `B` 鍵或 HUD 🔫 按鈕：花費金幣在原地 **佈署防禦砲塔**
  - `T` 鍵或動作欄 ⚙️ 按鈕：靠近標準砲塔時消耗 50 🪙 **進化砲塔模組**
  - `Esc` / `P` 鍵或 HUD ⏸️：**暫停**，打開暫停面板（目前構築、總數值、顯示設定）；面板裡的 🚪 **放棄任務**以失敗結算後回主選單（該局金幣與 DNA 照常入帳）
  - 滑鼠左鍵拖曳左下角 **虛擬搖桿** 同樣可進行精準走位
- **行動裝置 / 平板**：
  - **點畫面任一處，搖桿就跳到指尖**（動態搖桿），也可直接拖曳左下角的固定搖桿
  - 右下角整合 **動作欄**（⚡ 翻滾、🎒 戰術口袋道具、🔫 砲塔佈署、⚙️ 模組進化），點擊即可順暢施放
  - 已適配瀏海安全區、動態視窗高度（網址列收合不露白邊）、直向與橫向版面，並擋掉下拉刷新與雙擊縮放
- **戰鬥與戰術**：
  - 所有武器均為 **全自動索敵攻擊**，玩家只負責走位、翻滾躲彈幕與引爆場景物件
  - **連擊狂潮**：擊殺累加 Combo（3.6 秒無擊殺歸零），第 30 連擊與之後每 25 連擊觸發 7.5 秒狂潮，全武器攻速 +35%
  - **打擊頓挫**：擊殺 Boss 停格 80ms、精英怪 35ms，強化重擊手感

### 🧭 操作便利性（參考吸血鬼倖存者／Brotato／Halls of Torment）

- **升級卡封印／跳過**（每局各 3 次，數字在 `GAME_CONFIG.BANISH_PER_RUN / SKIP_PER_RUN`）：
  - 🚫 **封印**（卡片右下角）：該武器／配件本局不再出現在升級卡；只換掉那一張，其他兩張保留（不會變成免費重抽）。超武進化、特殊奇遇、急救包不能封印
  - ⏭️ **跳過**：這次不選任何升級，換 +25 本局金幣；還有待處理的升級會接著開下一輪
- **暫停面板**：每把武器的等級、到超武還差什麼（武器滿級 ✓／配件 Lv x/5、湊齊會標「可合成」）、配件、
  總數值（傷害倍率、冷卻、暴擊率／傷害、範圍、移速、拾取、減傷、生命、回復、承受傷害）、已取得的祝福與協同、封印／跳過剩餘次數
- **顯示設定**（主選單「🏠 養成基地」與暫停面板各一份、同步、存進存檔）：
  - 🔢 傷害數字：全部顯示／只顯示暴擊／關閉（只影響數字，文字提示與自己受傷的數字照常顯示）
  - 📳 畫面震動：開／關
  - 🕶️ 減少閃光：落雷亮度與光暈降低、Boss 大招紅閃降到 35%
- 回歸測試：`node tools/verify-qol.mjs`（20 項，全部走真的 DOM 點擊）

## 🎯 兩種作戰模式

出擊前先選模式。模式只描述規則差異，全部資料化在 [`js/modes.js`](js/modes.js) 的 `MODES`，新增模式不用動引擎。

| | 🏃 **生存者** | 🗼 **守塔** |
| :--- | :--- | :--- |
| 核心規則 | 怪物只追著你跑，撐過 8 分鐘 | 中央基地核心被圍攻，**破了就結束** |
| 砲塔／傭兵 | ❌ 完全沒有 | ✅ 主要火力來源 |
| 雜兵索敵目標 | 玩家 | 基地核心（Boss 仍鎖玩家）|
| 玩家武器輸出 | ×1 | **×0.6** |
| 金幣收入 | ×1 | **×2.2** |
| 砲塔費用 | — | **×0.6**（首座 36 🪙）|
| 失敗條件 | 特工陣亡 | 特工陣亡 **或** 核心被摧毀 |

**基地核心**（[`js/entities/Core.js`](js/entities/Core.js)）：14,000 HP，放在世界原點，玩家開場站在核心下方。雜兵貼上來就啃，HP 歸零即任務失敗；血量低於 30% 時 HUD 血條轉紅並呼吸警示。

> **關於同時攻擊數上限**：核心的啃食傷害只由最外圈的 16 隻結算（`main.js` 的 `CORE_MAX_ATTACKERS`），推擠阻擋則對所有貼上來的怪生效。這不是偷懶——實測若讓傷害隨怪數無上限累加，會有 249 隻同時貼著核心啃、瞬間衝到 2,972 DPS，核心開多少血都是幾十秒被秒。加上上限後進入核心的傷害穩定在 ~195 DPS，14,000 HP ≈ 完全不防守時 90 秒破核。

**實測難度曲線**（同一關、同一特工）：完全不防守 91 秒破核；繞著核心走位並有錢就佈防（最後 12 座砲塔、6 名傭兵、973 擊殺）撐到 7:05。要通關得比這個更會擺塔。難度要調就改 `modes.js` 的 `core.hp` 一個數字。

**進度分離**：兩種模式的**關卡最佳紀錄與解鎖進度各記一份**，但**養成完全共用** —— DNA、天賦、裝備倉庫、已解鎖特工跨模式共享。舊存檔（v3）自動遷移：原本的紀錄歸入生存者，已解鎖關卡兩個模式各複製一份，老玩家不會被鎖回第一關。

每日挑戰固定跑生存者模式（賣點是「同一天所有人條件一致」，跟著當前模式跑就破功了）。

## 🏰 守塔模式的戰術深度

原本的守塔只有「沿路擺四種塔、升級、專精二選一」，跟同類作品比起來確實單薄。這一輪補上四層：

### 🎯 八種戰術地基槽（`js/tdsockets.js`）

建塔點不再是「位置不同的同一格」。七張關卡共 82 個建塔點，每一格都掛一種加成，
滑鼠移上去、開建造選單、或點既有塔的檢查面板都會顯示**這一格會給什麼**：

| 地基 | 效果 | 為什麼有這個取捨 |
| :--- | :--- | :--- |
| 🎯 **高台** | 射程 +15% | 純粹的覆蓋率，適合擺在長直線中段 |
| ⚡ **加速齒輪** | 冷卻 -15% | 對高射速塔收益最大（加農砲幾乎無感） |
| ⚔️ **彈藥庫** | 威力 +20% | 通用，但擺錯塔線就浪費 |
| 🛡️ **裝甲基座** | 耐久 +30% | 守塔的塔不會被破壞，所以只在生存者的設施上有意義 |
| 💰 **金庫** | 每波結算利息 5%（單座上限 80 🪙） | 用「當下金幣」算，避免先蓋金庫再賣塔的套利 |
| 🔩 **穿甲塢** | 把護甲倍率往 1 拉近 25% | **均衡器不是增傷**：重甲 0.5→0.625，但已剋制的 1.5 會被拉低到 1.375 |
| 🎖️ **訓練場** | 每清空一波，這座塔永久 +4% 威力 | 愈早蓋愈強，逼你在「先鋪塔」與「先養塔」之間選 |
| 📡 **指揮所** | 半徑 220 內其他塔 +15% 傷害 | 多座不疊加（取最大），所以是「蓋一座好的」而不是「蓋一排」 |

> 這一輪同時修掉一個**一直沒生效的舊 bug**：地基加成原本直接寫進 `dmgMul` / `rangeMul`，
> 但塔一蓋好、升級、專精都會呼叫 `applyTDStats()`，而那支是**直接指派**這兩個欄位 ——
> 等於加成在蓋好的下一行就被洗掉。現在加成存在 `socketDmgMul` / `socketRangeMul`，
> 由 `applyTDStats()` 一起乘進來。`UI.js` 早就寫好四種加成的徽章顯示，只是資料端從來沒給過 `bonus`。

### 🌊 波次詞綴（`js/tdwaves.js`）

每一波可以掛詞綴改變「這一波怎麼打」，七關共 **32 波**掛了詞綴（全部 78 波裡），會在**下一波預告**上亮成標籤
（滑鼠移上去有完整說明）。六種詞綴：

| 詞綴 | 效果 |
| :--- | :--- |
| 🏃 **疾行** | 移速 +35%、血 -15% |
| 🛡️ **重甲縱隊** | 全體視為重甲（**刻意不動飛行怪** —— 否則「空襲＋重甲」會讓對空塔整條廢掉） |
| 🐜 **蟲潮** | 數量 ×1.5、血 -20% |
| 🦇 **空襲** | 追加一批飛行單位（沒有對空塔就是直接漏） |
| ⭐ **精英** | 血 +45%、賞金 +80% |
| 🧱 **要塞** | 血 +30%、移速 -15% |

詞綴的倍率全部相乘（`waveModMul`），所以「精英＋要塞＋重甲」的 Boss 波是真的硬。

> **別和「詞綴精英」搞混**：這一節的 ⭐ 精英是**寫在關卡資料裡的波次詞綴**（整波血 +45%、賞金 +80%）。
> v91 起守塔還會像生存者一樣**逐怪擲 `ELITE_AFFIXES`**（疾風／裝甲／巨獸／劇毒／封印），
> 那是另一套機制、另一個名字來源，兩者可以同時發生（波次詞綴 +45% 之後某隻怪再 ×2.5）。

### 🏰 王國升級（`js/tdkingdom.js`，快捷鍵 `K`）

用金幣買**全域、不佔建塔點、不怕被拆**的六條升級線，各三級：稅收（每波獎金 +20/45/80%）、
工程學（造塔與升級費 -8/16/25%）、彈道學（全塔威力 +10/22/35%）、光學（全塔射程 +6/13/20%）、
後勤（提前開戰每剩 1 秒多 +6/8/11 🪙）、英雄訓練（英雄攻擊與技能 +15/32/50%）。

這是「現在要把錢變成塔，還是變成未來的錢」這個問題的答案：工程學／稅收／後勤是複利，
彈道學／光學是即戰力，買錯順序會被下一波的詞綴教訓。

### ⭐ 實戰歷練（塔會自己長大）

每一座塔自己累計擊殺，**20 / 60 / 150 隻**升上 ★1／★2／★3（老練／精銳／王牌），
每星 +7% 威力、+3~5% 射程，塔頭上會出現金星。擺在交會口的塔會自己長大，擺在冷線的永遠是新手 ——
「餵哪一座塔」因此變成真的決策。檢查面板會顯示「擊殺 34（再 26 隻升星）」。

### 🖱️ 操作與打擊感

- **選中塔就畫射程圈**（含等級／地基／王國／星等的實際值），不用再心算覆蓋範圍
- **建造選單顯示 DPS／射程／對空對地**，以及 `剋輕甲` / `弱重甲` 的相剋標籤 ——
  「簡陋」往往不是玩法而是資訊：看不到 DPS 就只能憑圖示亂蓋
- **數字鍵 `1`–`4`** 直接選建造選單裡的塔（選單開著時數字鍵被選單吃掉，不會誤觸設施快捷鍵）
- **建造選單水平置中、永遠完整在畫面內**（v89）：選單是 `overflow: hidden` 容器底下的絕對定位元素，
  貼著建塔點擺會卡在螢幕邊緣；現在一律以**容器的實際方框**（不是視窗寬度）置中，上下依實測高度擇一
- **塔命中有火花**（顏色跟著傷害類型），**漏怪時畫面邊緣紅閃一次**（走 Boss 大招同一條管線，並尊重「減少閃光」設定）

### 🗺️ 程序化地圖與視野自適應（`js/tdprocedural.js` + `js/main.js`，v86 / v87 / v88）

出擊前可選 **橫屏 16:9 / 竪屏 9:16 / 自動跟隨螢幕**，守塔地圖會**每一局重新生成**：

- **地圖邊界隨視野伸縮**：橫屏沿用關卡原本的寬幅邊界（例：`td_fortress` 1600×1200），
  竪屏改成 920 寬的長條（高 1400~1680），核心固定在地圖下緣
- **道路每局不同**：七張圖各有一支生成器（蛇谷／雙叉／三門要塞／鑄造世界／紅色警戒／星海／魔獸），

> **v87 修掉三個安靜失效**（全都是玩家不會看到任何錯誤訊息的那種）：
> 1. `validatePathClearance()` 把「兩條路線通往核心的共用引道」也算成穿模，於是**每一組候選都被否決** ——
>    七張圖裡有六張其實從 v86 上線以來**從來沒有隨機化過**（連關卡手寫的原始路線都驗不過，就是這個徵兆）。

> 2. `td_fortress` 的竪屏生成器把兩翼的橫向跑道擺在北線折返點的同一段 y 上、內側轉角又和北線垂直段只差
>    20~70px，**10 次候選全被否決**，每局都退回橫幅原始路線、再被硬拉伸進直屏。現在兩翼改由地圖左右緣的
>    中段切入，各路線保證拉開 150px 以上。
> 3. `randomizeTDLevel()` 的「路線出界」保險原本用**餘裕 8px** 判定，但生成器是**刻意貼著地圖邊緣**設計的
>    （入口點就落在 `bounds.minY`），所以每一局都被觸發、把整張圖**非等比拉伸**去填滿內縮框，
>    順手把剛好過關的路線間距壓爛。改成只有真的超出邊界才啟用。
>
> 另外，七張路面貼圖在 v86 是「有下載、有預快取、有解碼，但 `TD_PATH_IMAGES` 從頭到尾沒有人讀取」——
> 現在真的畫在路面上；而且因為有靜態圖層烘焙，**畫貼圖反而比 v86 的逐幀向量畫法更快**
> （實測每幀 `td_canyon` 14.7ms vs 28.1ms、`td_starcraft` 23.4 vs 28.6；沒有烘焙的逐幀貼圖要 36~41ms）。

> **v88 修掉「豎屏變橫屏整個畫面拉伸變形」**：`#game-container` 有 `transition: width .25s, height .25s`，
> 而切換 `orient-*` 類別**不會**觸發 `window.resize` —— `setOrientation()` 在類別換掉的當下讀
> `clientWidth/Height`，讀到的是**轉場剛開始的舊尺寸**，之後 CSS 把畫面拉成新比例、畫布卻還停在舊比例，
> 於是整個遊戲被非等比拉伸（實測 1280×800 切橫屏縱向被壓 11%、竪屏↔橫屏互切可到 2.1 倍）。
> 裝置轉向（viewport 真的變了）也一樣，因為 `resize` 事件是在轉場之前就送出的。
> 現在兩道保險：`ResizeObserver` 盯著容器，尺寸一變就重算視野；`_applyCanvasSize()` 的畫布尺寸
> **以畫布自己的 CSS 方框為準**（`getBoundingClientRect() × dpr`），所以就算帳上的 `sw/sh` 一時過期，
> 畫面也不可能被拉歪。轉向時地圖**不會**重新生成（否則塔會在半空中被換位置），只重新取景。
>
> 另外，設定「竪屏」但手機橫放時，那個 9:16 窄框只剩 **219px 寬**，HUD 與右側按鈕會全部疊在一起 ——
> 這種「方向不符**而且**窄框擠不下（寬度 < 320px）」的情況現在**改用整張畫面（自動版面）並在 HUD 下方提示**
> 「螢幕現在是橫屏，與設定的『竪屏』不符 —— 先用自動版面，轉回竪屏就恢復」（10 秒後自動淡出），
> 裝置轉回設定方向就當場恢復。桌面上把視窗拉成直向、想看 9:16 版面（寬度仍有 450px 左右）的行為
> **維持不變**，那是刻意的預覽用法。

> **v89 修掉「建造選單有時會被卡到」**：選單是 `#game-container`（`overflow: hidden`）底下的絕對定位元素，
> 舊版有兩個毛病，而且都只表現成「看不到」不報錯——
> (1) 夾邊界用 `window.innerWidth`（整個視窗）而不是容器的實際寬度：竪屏的容器是**置中的 9:16 窄框**
> （1280 的視窗裡只有 405px），貼著右邊的建塔點會把 306px 寬的選單推到容器外，實測**右側被切掉 149px**；
> (2) 上下用寫死的 `pos.y < 320` 決定，但選單實際高 **461~480px**，點在畫面中段時放上方一定爆出頂端，
> 實測**上方被切掉 170px**。
> 現在一次量實測尺寸、一次算完：**水平一律在容器內置中**（不再貼著建塔點卡在螢幕邊緣），
> 垂直依實測高度選上方／下方，上下都塞不下才置中且**自動縮高度讓內容自己捲**（小手機 360×640 實測
> 306×410 剛好放得下）。`css/style.css` 也拿掉了 `transform: translate(-50%, …)` 位移——
> 位移會讓「夾在容器內」的計算對不上實際方框。

> **v90 把守塔的人物放大 30%**：守塔鏡頭拉遠到整張地圖放得進畫面（zoom 0.7）之後，
> 英雄只有 **53px** 高、怪物 **48px**、兵營小兵**待機 34px** —— 比塔（**52px**）還小，
> 使用者反映「TD 的人物有點小」。現在 `js/config.js` 新增 `TD_CHAR_SCALE = 1.3`：
> 英雄 `96×99` 世界px（螢幕 69px）、怪物 `79px` 高（螢幕 55px）、小兵格 `104×83`。
>
> **只放大「畫出來的」尺寸**：碰撞半徑（英雄 18、怪物 14、小兵 13）、傷害、射程、擊退、
> 波次血量全部不動 —— 這類改動最怕順手把 `radius` 也乘上去，那會同時改掉碰撞、卡位與擊退手感，
> 所以 `tools/verify-td-deep.mjs` 直接把三件事釘住：倍率有套上、`drawRadius` 有跟著、
> `radius` 沒有變。血條（英雄 `-32 * k`、怪物 `drawRadius` ）、狀態光圈（冰凍／眩暈／減速／
> 精英光環）、槍口與雷射起點也都改成跟著放大後的半徑走，否則會縮進身體裡看起來像破圖。
> **生存者模式維持原尺寸**（`drawScale` 在每次 `start()` 一起歸零，守塔才給 1.3），
> 黎曼魯斯戰車屬載具也刻意不放大。

> **v91 把守塔的難度與生存者分開**：難度原本是**一個全域設定**，兩件壞事因此發生 ——
> (1) 難度解鎖只看**生存者 13 關**（`DIFF_REQUIRED_LEVELS` 就是 `LEVEL_ORDER`），所以守塔玩家把
> 七張圖全打通，下一階難度仍然是鎖的；`recordDifficultyClear()` 更把 `td_*` 關卡的勝場直接丟掉
> （`if (!DIFF_REQUIRED_LEVELS.includes(levelId)) return null;`），守塔進度**靜默消失**。
> (2) 說明列了六個軸，其中「生成密度」與「菁英機率」**在守塔完全沒生效** ——
> `spawnMul` 只被生存者的 `Spawner.js:140` 讀、`eliteChanceMul` 只被 `Spawner.js:172` 讀，
> 而 `TowerDefense.js` 開頭自己註明「不擲精英」。玩家看著說明按困難，實際只有血量／受傷／移速／金幣
> 四個軸。
>
> **現在難度是分模式的**：存檔用兩個欄位（生存者 `difficulty`、守塔 `tdDifficulty`），
> 解鎖各自認自己的關卡清單（`modes.js` 新增 `difficultyLevels`：生存者 12 關〔扣掉無盡〕、守塔 7 關），
> `diffClears` / `diffUnlocked` 都加了模式維度 —— 這與**關卡解鎖早就分模式**（`save.isUnlocked(id, modeId)`）
> 一致，難度沒分才是那個不一致。舊存檔走遷移：扁平的 `diffClears` 歸給生存者，
> `diffUnlocked` **同時鏡射給守塔**（舊玩家不會被鎖回去），守塔的難度沿用他原本選的那一個。
>
> **守塔補上缺的兩個軸**（`js/systems/TowerDefense.js`）：
> - **密度**：波次佇列的時間軸除以 `spawnMul`（`(gi * GROUP_STAGGER + k * grp.gap) / density`），
>   與 `Spawner.js:140 interval /= rules.spawnMul` **同語意 —— 每波總數不變、只有到達變密**。
>   刻意不去乘怪物數量：那會讓地獄同時「更多怪」又「更快到」，是雙重加壓，而守塔沒有 `MAX_ENEMIES`
>   上限（41 隻同場實測 90 帧 median 33.3ms，沒有效能懸崖，但沒必要去踩）。
> - **菁英機率**：逐怪擲 `js/config.js` 的 `ELITE_AFFIXES`（與生存者**同一個池子、同一組數值**，
>   抽選改由 `rollEliteAffix()` 統一供給），機率 `min(0.45, min(0.30, 0.04 + (波-3)×0.015) × eliteChanceMul)`，
>   前兩波為 0 —— 開場就丟巨獸只是勸退。精英的 `exp` 會經 `bounty()` 自動反映成賞金。
>
> 難度壓力實測（td_canyon，同一份波次表 170 隻）：

| 難度 | 敵人血量倍率 | 總血量 | 全波到達窗 | 第 1 波跨度 | 菁英機率（第 3／6 波） | 預期詞綴精英 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 🐣 輕鬆 | ×0.65 | 570 | 79.5s | 9.5s | 4% / 8.5% | 12 |
| 🦆 標準 | 基準 | 877 | 67.6s | 8.1s | 4% / 8.5% | 12 |
| 🔥 困難 | ×1.9 | 1,667 | 37.6s | 4.5s | 6.4% / 13.6% | 19 |
| 💀 惡夢 | ×3.0 | 2,632 | 28.2s | 3.4s | 8.8% / 18.7% | 27 |
| ☠️ 地獄 | ×4.2 | 3,684 | 22.5s | 2.7s | 12% / 25.5% | 36 |

> 密度確實只壓縮時間軸：五個難度的**每波怪數一模一樣**（170），第 3 波跨度 6.70s → 2.23s
> 正好是地獄的 ×3.0。到 22.5 秒一波時壓力來自「同一段路同時更多怪」，而不是「怪更多」。
> 這也是為什麼沒有另外給守塔一份難度表：它的關卡階梯（`tdlevels.js` 的星等與 `dnaMult`）本來就在，
> 全域難度是玩家自己選的加壓層。

### ✅ 回歸測試（`tools/verify-td-deep.mjs`）

```bash
node tools/verify-td-deep.mjs        # 103 項：關卡資料／道路生成器（純 Node）+ 實機（Playwright）
```

**為什麼要單獨一支**：既有的 `verify-levels.mjs` / `verify-balance.mjs` 看不到 `td_*` 關卡 ——
守塔關卡是在 `js/tdlevels.js` 裡 `Object.assign(LEVELS, TD_LEVELS)` 併進去的，而 `js/levels.js`
本身不含它們，純 Node 的腳本只 import 後者就會少掉七張圖。

這批功能的失效方式全都很安靜、也大多不會拋例外，所以每一條都驗**資料層 → 塔身上的實際數值 → 畫面／DOM** 三段：

- 八種地基各蓋一座，比對 `dmgMul` / `rangeMul` **比值**是否真的是 1.20 / 1.15
  （v83 那個「八種地基一條都沒生效」的 bug，這裡是唯一守得住的地方）
- `applyTDStats()` 連呼兩次不洗掉也不疊加
- 星等門檻（20/60/150）、`addKill()` 只在跨門檻那一次回 `true`、滿星後回 `false`、`eliteNext()` 回 `null`
- 建造選單的數字鍵 `1`–`4` **走真的 keydown 事件**（直接呼叫函式就測不到「被設施快捷鍵先吃掉」這個 bug）
- 王國升級買完後，**已經在場上**的塔立刻吃到 +10% / +6%（`applyKingdom()` 有沒有推）
- 詞綴的倍率數字（疾行 1.35、蟲潮 ×1.5、精英賞金 ×1.8）與「多個詞綴相乘」、未知詞綴被忽略
- 開打後**佇列每一項都帶著這一波的詞綴**（只驗預告文字會漏掉「預告有、佇列沒有」）
- 滿星塔的射程圈與星等繪製、`#inspect-type` 印出「⭐3 王牌（擊殺 150，已滿星）」
- 七張守塔地圖各開局跑 600 帧不拋例外
- **七張圖的原始路線本身**必須通過 `validatePathClearance()`（生成器的門檻不能比手寫資料還嚴）
- **橫屏／竪屏各 25 局**：每一局都真的和原始路線不同、全部落在地圖內、建塔點補滿到目標數、
  而且「生成出來的路線自己也要過 clearance」（這一條就是 v86 那六張圖從沒隨機化的守門處）
- **路面貼圖真的畫在路面上**：把 `TD_PATH_IMAGES[key]` 暫時拔掉，路面同一點的顏色必須改變；
  另外驗圖層快取（同縮放連畫兩帧不重烘）、快取鍵帶關卡 id 與縮放、像素上限，以及
  「沒有離屏圖層時退回逐幀繪製」與圖層落在同一位置（相機位移有沒有正確扣除）
- 切到竪屏再出擊，地圖邊界真的變成長條、路線不出界、建塔點 10/10 且跑 60 帧不拋例外
- **畫面不會被拉伸**（v88）：切 橫屏 → 竪屏 → 自動 各等轉場跑完後，量 `canvas.width / (CSS 寬 × dpr)`
  必須是 1（實測最大偏差 0.00%），而且遊戲記下的 `sw/sh` 要等於實際大小（守塔縮放與相機靠它）
- **裝置轉向也要跟著更新**（v88）：把 viewport 依序換成 844×390 / 390×844 / 1280×800，
  每次都重新量畫布比例與 `sw/sh` —— 這一條顧的是「`resize` 事件比 CSS 轉場更早送到」那個時序問題
- **方向不符的窄框處理**（v88）：手機橫放（844×390）卻設定竪屏時，窄框只剩 219px，必須**改用自動版面**
  並顯示提示；轉回直向要當場恢復竪屏版面、提示消失。同時必須顧到反面：桌面橫視窗（1280×800）選竪屏時
  窄框仍有 450px，**要照設定顯示、不提示**（那是刻意的 9:16 預覽用法，不能被一起改掉）
- **建造選單不會被容器切掉**（v89）：把點擊位置直接餵給 `UI.showBuildMenu`（不去推相機——相機每幀會被
  clamp 回地圖邊界，反推座標不可靠），在四角、正中央與畫面中段各量一次方框必須完整落在容器內，
  而且**水平置中偏差 ≤ 1.5px**；竪屏那一段另外驗「容器真的變窄（< 900px）」＋「點最右邊仍完整在畫面內」，
  免得轉場還沒跑完時這條測試悄悄退化成跟橫屏一樣
- **守塔人物放大只動畫面**（v90）：`drawScale === TD_CHAR_SCALE`、怪物 `tdDrawScale` 也吃到，
  但 `radius` 必須**原封不動**（用 `drawRadius / radius === 1.3` 釘住）；另外一條反面案例是
  「玩完守塔再回去玩生存者，`drawScale` 要回到 1」——避免哪天只有守塔那條路會設它
- **守塔吃得到密度與菁英**（v91）：同一份波次表在標準／地獄各排一次隊，逐項比對「怪數完全相同、
  但到達間隔剛好是 `1 / spawnMul`」（地獄第 3 波跨度必須是標準的 1/3，容差 0.02 秒）；
  菁英則用 stub 骰子強制命中，驗 `isElite`、詞綴數值有乘上去（hp／speed／exp）、
  賞金跟著 `exp` 提高、`spriteScale` 與 `radius` 同步，以及**反面案例**「前兩波機率是 0」
  （`eliteChance()` 回 0）與「機率吃難度倍率」（地獄 0.255 對標準 0.085）
- **難度是分模式的**（v91）：守塔的地獄不會滲進生存者，兩邊各自讀自己的欄位
  （`g.diffKey` 與 `save.data.difficulty` / `tdDifficulty` 交叉比對）

Boss 血量依實測玩家 DPS 曲線（2 分約 200、5 分約 700、8 分約 1,200 DPS）反推每場 20~35 秒的理論擊殺時間，再乘上各關難度係數。

雜兵的成長係數集中在 [`js/levels.js`](js/levels.js) 的 `enemyScale(gameTime, level)`，Spawner、胞囊孵化、死亡裂解共用同一份公式：

- **血量** = `(1 + 時間/60 × 0.55) × 3 × 關卡 hpScale × 規則 enemyHpMul`，無盡關另疊 `1 + 時間/300`；10 分鐘後再乘一個二次項 `1 + (分鐘-10)² × 0.012` 追上玩家的後期輸出。1 分鐘 ×2.4、3 分鐘 ×4.0、5 分鐘 ×5.7、8 分鐘 ×8.1、24 分鐘 ×47.6（舊曲線 24 分鐘只有 ×7.7）。8 分鐘熔爐關為 ×6.5 × 上述係數
- **傷害** = `1 + 0.105 × 分鐘 + 0.052 × 分鐘^1.4`（`enemyDmgScale`）：1 分鐘 ×1.16、3 分鐘 ×1.56、8 分鐘 ×2.82、20 分鐘 ×6.55、30 分鐘 ×10.2、40 分鐘 ×14.3。**沒有折點、沒有硬封頂**（見下方「難度曲線為什麼是階梯」）
- **屬性壓力** = `1 + 0.09 × 分鐘 + 0.02 × 分鐘^1.3`（`enemyElemScale`）：1 分鐘 ×1.11、8 分鐘 ×2.05、20 分鐘 ×3.78、40 分鐘 ×6.9 —— 這是屬性持續傷害的絕對值，見下方〈屬性攻擊〉
- **地形傷害** = `1 + 0.16 × 分鐘 + 0.03 × 分鐘^1.35`（`hazardDmgScale`）：常數的地形傷害在中期就等於 0，所以毒池／岩漿／地雷的傷害與屬性附著都隨時間同步成長
- **移速** = `ENEMY_SPEED_BASE × enemySpeedMul × min(1.5, 1 + 時間/60 × 0.03)`，`ENEMY_SPEED_BASE = 1.6`（全局旋鈕，見下）

#### 「敵人太脆，近不了身」是怎麼修的（第三輪）

玩家回報後用 `tools/probe-enemy-pressure.mjs` 量出兩個**同時存在的**瓶頸，缺一不可：

| 瓶頸 | 量測 | 修法 |
| :--- | :--- | :--- |
| 血量跟不上玩家輸出 | 舊曲線每分鐘只成長 ×0.28（8 分鐘 ×3.2），而玩家輸出 2→20 分鐘成長 413 倍 | 斜率 0.28 → **0.55**，並全局 **×3** |
| 走不到玩家面前 | walker 從生成距離 500px 要走 **5.6 秒**，但只活 1.0 秒 | `ENEMY_SPEED_BASE = 1.6`，行軍降到 3.5 秒 |

只改血量不夠：×2 的時候雜兵存活 4.1 秒、行軍 5 秒，接觸率仍然是 **0%**。
只改移速也不夠：牠會在更近的地方被打掉。兩個都改之後才成立。

實測（標準難度、真實主迴圈、玩家站著不動）：

| 情境 | 舊 | 新 |
| :--- | ---: | ---: |
| 單隻 walker 接觸率（5 分） | 8% | **100%** |
| 單隻 walker 接觸率（8 分） | 100% | 100% |
| 一群 30 隻的接觸率（1／2／5／8 分） | 81／84／91／92% | **100／100／100／100%** |
| 玩家 15 秒內受到的傷害（5 分） | 0 | **25** |

注意「單隻」與「一群」的差別：單隻在 2 分鐘仍然到不了（混戰中總有幾隻會到，
所以一群的接觸率才是體感指標）。`ENEMY_SPEED_BASE` 刻意做成**全局單一旋鈕**而不是
逐隻調速度 —— 逐隻調會讓 13 種怪的手感差異（蛇行／撲擊／風箏）一起跑掉。

#### 發射投射物的敵人（玩家要求「多一些」）

原本遠程敵人只佔波次池 **15.1%**，而且 22 個波次完全沒有遠程怪。現在：

- 遠程權重**翻倍**，並為原本沒有的 22 個波次補上 `spitter`（權重維持不變，等比縮小其餘）
- 每一關的遠程佔比 **≥ 20%**（最高波次），全關卡平均 **45.5%**
- 遠程怪本身也要撐得住才射得到：`spitter` 42 → **95** HP、`sniper` 38 → **80** HP，
  射擊冷卻 2.4 → **2.0** / 3.6 → **3.0** 秒
- 實測 12 隻遠程怪 30 秒共 147 發（每隻每分鐘 **24.5 發**）

契約（`verify-balance.mjs`）：每一個波次都要有遠程敵人、每關最高波次 ≥ 20%、
全關平均 ≥ 25%、遠程怪血量下限。

傷害成長是刻意加的：原本只有血量會漲，後期敵人只是變厚而完全不變兇，體感從「威脅」淪為「磨」。以熔爐關的攻城巨像為例，單次撞擊從 24 漲到 43，配合 0.5 秒無敵時間，最壞情況進傷由 48 HP/s 提高到 86 HP/s。

**終極首領的實際門檻**：30 秒內擊殺分別需要 1,400 / 1,833 / 2,267 / 2,933 DPS。一局約可升到 16~17 級（8 分鐘約 1,400 隻雜兵、平均 1.5 exp），扣掉養一把超武要花的 10 張升級卡，實戰輸出大約是「一把超武 + 三把半殘武器」，因此**第四關實質上需要靠局外裝備補足**。

#### 難度曲線為什麼是階梯，以及怎麼把它拉平（第四輪）

玩家回報：「**過了一個強度就基本不死了**」。這句話精準描述了當時的曲線形狀 ——
不是「太簡單」，是**階梯**：某個時間點之前太癢，之後一次跳太多，最後又完全平掉。

**先找出階梯本身。** 舊的傷害曲線是一條折線再加一個硬封頂：

```
舊： min(12, min(5.5, 1 + 分鐘×0.14) × (1 + max(0, 分鐘-10)² × 0.010))
                 ↑ 10 分鐘處斜率從 0.14 突然跳成 0.14 + 0.2×(分鐘-10)   ↑ 約 24 分鐘撞到 12 倍就再也不動
```

三個不連續點：10 分鐘的**折點**、24 分鐘的**硬封頂**、以及開場係數（`OPENING.hpMul ×2.5`）
用**線性**淡出 —— 線性在兩端各留一個斜率斷點。新的曲線改成處處可微的單一條成長式
（`1 + 0.105×分鐘 + 0.052×分鐘^1.4`，沒有折點也沒有硬封頂），開場淡出改用 `smoothstep`
（兩端導數都是 0，端點值不變所以中段平衡不動）。`tools/verify-balance.mjs` 現在用
**數值微分**守住這件事：相鄰分鐘的斜率變化必須 < 25%，且 60 分鐘仍嚴格大於 40 分鐘。

**但光把折線拉直不夠 —— 真正的瓶頸是「傷害只有一條通道」。**
玩家的防禦是多層相乘加上限（護甲 ≤50%、鐵壁藥水再 ×0.5、聖域再 ×(1−resist)、護盾吸收），
再加上最關鍵的 **0.5 秒無敵影格**。相乘之後，一次性傷害的通道被鎖死在「每秒最多 2 下」：

```
單怪接觸 DPS 上限 = 基礎接觸傷害 × 傷害倍率 ÷ 0.5 秒
```

於是只要「生命 ＋ 每秒回復」超過這個上限，**場上有幾隻怪都一樣殺不死你**。
這不是數字不夠大，是結構問題：把傷害數字再調高只會讓折線更陡，階梯更明顯。

**所以補上第二條與第三條通道 —— 兩者都不吃無敵影格：**

| 通道 | 機制 | 為什麼不受無敵影格影響 |
| :--- | :--- | :--- |
| **屬性攻擊**（`config.js` 的 `ELEMENTS`） | 敵人攻擊帶 🩸物理 / ☠️劇毒 / 🔥燃燒 / ⚡電擊 / ❄️冰凍。命中時除了當下傷害，還在玩家身上留下**可疊層的持續傷害** | 持續傷害在 `Player.update` 裡**逐幀結算**，走的是 `tickPlayerElements()` 而不是 `takeDamage()`，所以完全繞過 `invulnerableTimer` |
| **地形傷害**（`Hazards.js`） | 毒池／岩漿／流雷／流沙／縮圈等地面區域的傷害**隨時間成長**，並且會附上對應屬性 | 同上；而且被無敵影格擋下當下傷害時，屬性層數**照樣附著**（`hurtByHazard()`） |

四種屬性各有**護甲穿透**（`armorPierce`），所以「堆滿 50% 護甲」不再是萬靈丹：
劇毒 0.5、電擊 0.6（金屬護甲反而導電）、燃燒 0.35、冰凍 0.25。
持續傷害的公式刻意混了兩個成分：

```
每秒傷害 = ( dotFlat × enemyElemScale(時間) + dotPct × 玩家最大生命 ) × 層數
```

`dotFlat` 那項隨時間成長（跟物理傷害同一條時間軸），`dotPct` 那項隨玩家生命成長 ——
合起來讓「後期傷害自動追上玩家的成長曲線」，既不會在前期一擊秒殺，也不會在後期被回復量吃掉。
疊層有節流（剩餘時間還很長時不再加層），所以一群怪不能在半秒內把毒疊滿。

**對策不是沒有，但需要動作：** 💧**回復泉**與 🛡️**聖域**會**淨化身上的屬性層數**，
而每關的機制每 30~45 秒就會生一個。中了毒不一定要逃，也可以主動去找泉水 ——
「站著不動」有代價，「移動到正確的位置」有回報。

**量化（`tools/probe-*.mjs` 與實機模擬，固定建置、站著不動、各 60 秒）：**

| 情境（標準難度，同一套滿級建置） | 舊：承受 DPS | 新：承受 DPS |
| :--- | ---: | ---: |
| 3 分鐘（護甲 0%） | 1.6 | 7.4 |
| 5 分鐘（護甲 0%） | 5.0 | 10.5 |
| 3 分鐘（護甲 50%） | 2.5 | 7.0 |
| 5 分鐘（護甲 50%） | **1.1**（比 3 分鐘還不痛 ← 這就是階梯） | 11.9 |
| 8 分鐘（護甲 50%） | 3.9（滿血活著） | 13.4（**死亡**） |
| 12 分鐘（護甲 50%） | 15.2 | 27.5 |

舊版「護甲 50%」那一列是非單調的（3 分鐘比 5 分鐘痛、8 分鐘幾乎無傷），
新版是單調上升的平滑曲線，而且**堆滿護甲也會在 8 分鐘被殺死**。

**開局有沒有變難？** 用 10 次取樣的新手建置（1 把武器、無配件、100 HP、5 分鐘上限）對照：

| 情境 | 舊：死亡時間中位數 | 新：死亡時間中位數 |
| :--- | ---: | ---: |
| 站著不動 | 33 秒 | 24 秒 |
| 一般風箏走位 | 167 秒 | 160 秒 |

風箏走位幾乎不變（−4%），只有「站著不動」變得更該死 —— 這正是這一輪想修的方向。

量子足球先前等於壞掉（Lv5 在密集怪群只有苦無的 1/4），所以它不維持原數值，而是調到同類武器的水準：
Lv5 約為苦無的 60%、量子星雲球與雙刃風暴相當。
為了維持強度，火箭（45→35）、雷電（36→32）、相位飛刃（34→22）、相位風暴（55→45、冷卻 0.15→0.3）、
量子星雲球（55→45）的單發傷害有下修，足球彈跳次數改為 4~8（原 5~16，舊的次數只算撞世界邊界）。

**裝甲值 vs 子彈數**：迴力鏢與軌道炮的傷害都在 `WeaponManager` 內結算——軌道炮在 `fireRailgun` 直接對直線上所有敵人 `takeDamage`，
迴力鏢則走一般的投射物碰撞（在 `main.js`），所以「去回兩段都能打」是靠 `rehit` 讓命中清單定時清空，不是靠兩顆彈體。

**環繞型武器的傷害節奏**由 `WeaponManager` 的 `ORBIT_REHIT`（0.4 秒）決定：同一片刀刃每 0.4 秒才能再打到同一隻敵人。超武的環是永久旋轉（`baseCooldown: 0`），只要規格沒變就原地保留、不重建——早期版本每 0.08 秒重建整組環，等於不斷清空命中清單，造成每目標 400+ DPS 的失控輸出。彈跳球同理走 `SOCCER_REHIT`（0.5 秒），不然一顆球對同一隻怪一輩子只能打一次，24 次彈跳形同白給。

十把超武的單體 DPS 目前落在 **150~420**，且**每一把都強於自己滿級的基礎型態**。

### 🎒 四把武器怎麼「帶」在身上

主手那一把會**追瞄最近的敵人**；其餘三把以固定角度**背／掛在身上**（`HELD_MOUNTS` 掛載點表），
而且分兩層畫：斜背與後腰的武器畫在**角色之下**（會被身體擋住一部分，像真的背著），
主手與腰前的畫在角色之上。

這不是純粹的美術選擇 —— 四把武器原本共用同一個手部原點，實測兩兩重疊率高達 **54~99%**
（kunai/rocket 87%、rocket/molotov 99%），而且火箭/軌道炮這種長管武器會直接橫在角色臉上。
改成掛載點之後，`tools/verify-art.mjs` 量到 **兩兩重疊 0%**（這一條仍然成立），
但可見比例已經退化了：**slot0(front) 31% / slot1(back) 49% / slot2(front) 33% / slot3(back) 7%**，
低於腳本自己設的 45% 門檻（可見比例 = 武器本體像素扣掉被角色剪影遮住的部分）。
`verify-art.mjs` 另外還有 4 條輪廓光檢查沒過（duck 70%、rabbit 64%、cat 58%、techpriest_goose 3%，
門檻是「≥ 12 個亮點且 ≥ 70%」）—— 這幾條在 v83 基準線上就是同樣的數字，屬於**既有落差、不是 v86/v87 造成的**，
要修得動 sprite 剪影與材質層，已在「已知技術債」記著。

### 🌟 超武覺醒（進化後還能繼續升級）

超武進化後 `level` 不再停在 1：**每升一級傷害 +15%**（`WEAPONS[evoId].evoGrowth`，上限 5 級），
升級卡會標成「超武覺醒 3 → 4」。

為什麼要這個：在這之前，超武的 `level` 永遠是 1、也不會出現在升級三選一裡 ——

覺醒把「進化」從終點變成另一個起點：滿級 Lv5 的超武是基礎傷害的 **1.6 倍**。

## 📏 射程 ↔ 攻擊力 ↔ 穿透：每把武器的三軸定位

玩家指定的設計原則：**「射程越短攻擊力越強」要對所有武器成立，而且穿透能力要有區隔。**
三條軸合起來就是每一把武器的定位，資料全部在 [`js/config.js`](js/config.js)：

```
短射程 ── 高單發傷害 ── 低穿透   環鋸(34px)、火海(55)、奇點環(62)、守護輪盤(65)
中射程 ── 中單發傷害 ── 中穿透   相位風暴(420)、苦無(480)、迴力鏢(520)、爆彈槍(600)
長射程 ── 低單發傷害 ── 高穿透   風暴爆彈槍(660)、軌道炮(900)、殲滅光束(1200)
```

**為什麼要做成「一條規則 + 一份資料」而不是逐把調數字。** 先前只有霰彈槍有射程倍率，
其餘武器把射程拉長是純賺；穿透則散在各個 `fire` 方法裡自己讀 `def.pierce`、自己寫
魔術數字 `9999`、自己接 `Array.isArray` —— 於是「穿透有沒有區隔」完全取決於誰記得寫。
現在三個部件各自只有一處：

| 部件 | 位置 | 作用 |
| :--- | :--- | :--- |
| `WEAPONS[*].range` | config.js，**28 把全部必填** | 宣告射程。「範圍就是射程」的武器（環繞／火海／脈動／揮砍）由 `radius` 自動補齊，避免兩份數字漂移 |
| `rangeDamageMul()` | config.js | 規則本體：`clamp((320 / 射程)^0.45, 0.6, 2.2)`。**壓縮指數 0.45** 是必要的 —— 射程從 34px 到 1200px 差 35 倍，線性反比會變成 35 倍的傷害差，那不是定位而是失衡 |
| `weaponRangeTier() × rangeTradeoffMul()` | `fireWeapon()` **單一呼叫點** | ① 宣告射程的定位倍率 ② 玩家拉長射程之後的取捨。契約 D8b 要求這裡只能出現一次，否則就是重複計算 |

**升級不會被這條規則吃掉。** 等級成長也會放大射程（守護輪盤 L1 65 → L5 95、烈焰新星
110 → 165），所以取捨用「拉長後的射程 ÷ 原始射程」的**比值**，而不是絕對值 ——
升級拿到的射程是獎勵，不反過來扣傷害。實測（貼身假人、12 秒、逐把量測）：

| 射程倍率 | 28 把武器的傷害比 |
| :--- | :--- |
| ×1（原始） | 1.000 |
| ×1.75（高能燃料滿級／烈焰之觸／赫米斯型態） | **0.756 ~ 0.810**（全部下降，無一例外） |

**穿透的區隔**由 `declaredPierce()` 統一提供，資料上分成三種語意：

- `pierce: 數字或等級陣列` —— 線型武器（12 → 10 把）。霰彈槍 2 → 風暴爆彈槍 4 → 雙刃風暴 8，**長射程的線型武器穿透至少是最短射程的 2 倍**（契約 D7）。
- `pierceAll: true` —— 範圍型與光束型（16 → 18 把）：火海、脈動、旋轉領域、貫穿光束，以及**彈射型**的足球／量子星雲球（撞到不消耗，吃群靠 `bounces`）。
- 濺射型（爆彈槍／火箭／鯊魚核彈）穿透 ≤ 2 —— 它們吃群靠爆炸半徑，不是靠穿透（契約 D7b）。

**重新定位的實際幅度**（同一個假人、同一把武器的滿級，量測 28 把的 DPS 變化）：

| 位置 | 武器 | DPS 變化 |
| :--- | :--- | ---: |
| 最短射程 | 奇點環 +19%、能量劍 +18%、環鋸 +17%、永恆力場 +11%、燃油煉獄 +10% | **+8% ~ +19%** |
| 中程 | 電漿風暴 1.00、相位飛刃 0.99、鏈鋸劍 0.98、龍息 0.98 | **±2%** |
| 最長射程 | 風暴爆彈槍 −15%、爆彈槍 −12%、殲滅光束 −11%、軌道炮 −9% | **−9% ~ −15%** |

中位數 0.98、全距 0.85~1.19 —— 是**定位改變**，不是整體變強或變弱。
`tools/verify-balance.mjs` 的 D 組 15 條契約守住這件事：資料必填、規則單調、
最短射程三分之一全部拿到加成、最長射程三分之一全部付代價、穿透至少有 4 種值、
線型武器兩端穿透差 ≥2 倍、彈射型必須 `pierceAll`、以及射程取捨在原始碼層級只有一處。

特別注意 **`baseDamage` 是「校準後」的值**，不是可以直接看的數字：實際輸出 =
`baseDamage × 射程定位倍率 × 玩家射程取捨`。所以 `tools/verify-weapons.mjs` 的粗算 DPS
必須把射程定位算進去，否則烈焰新星會被誤判成被支配（baseDamage 24 看起來只有 13 DPS，
實際是 24 × 1.62 = 39）。

**加成是怎麼套上去的（`tools/verify-gear.mjs` 22 項）**

玩家身上有四桶加成，語意不同、不可混用：

| 桶 | 來源 | 語意 | 誰負責套 |
| :--- | :--- | :--- | :--- |
| `player.meta` | 天賦 ＋ 裝備詞條 | 加在**角色基礎值**上（`baseSpeedMul = 角色基礎 + meta.speed`） | `WeaponManager.applyPassives()` |
| `player.legendary` | 傳奇特效的屬性加成 | 加在**最終倍率**上（音速突進／引力漩渦；極限超頻併入 cdr） | 同上 |
| `player.runMuls` | 單局興奮劑、每日詞綴 | **乘法** | 同上 |
| `player.blessing` | 局內祝福（暴擊率、暴擊傷害、經驗） | 加在**總和欄位**上（`metaCrit = meta.crit + blessing.crit`） | 同上 |

`applyPassives()` 是唯一的套用點，語意一律是「重算」而不是「累加」—— 每次升級都會重跑。

第四桶（`blessing`）是「增傷祝福的風險要高於增益」那次改動時補上的：祝福原本直接寫
`p.metaCrit += 0.15`，而 `metaCrit` 是每次升級都會被重算的**總和**欄位 —— 選了
暴擊風暴之後 `metaCrit` 一直是 0，祝福等於沒選到（同樣的坑第三次）。現在總和一律
寫成「永久層 ＋ 局內層」，祝福只動局內層。

為什麼要拆成這些桶：舊寫法把局外加成直接寫進 `damageMultiplier` / `speedMultiplier` /
`magnetMultiplier`，而 6 行之後的 `applyPassives()` 又把這三個欄位從頭重算，只靠
「對方剛好記得讀回 `metaDmg` / `baseSpeedMul`」才活著。這種耦合每加一個欄位就會靜默失效，
實際上已經踩到四次：

1. **傳奇特效「音速突進 +12%」完全沒生效** —— 它加到 `speedMultiplier` 之後，
   同一輪的 `applyPassives()` 立刻把它覆蓋掉（實測 `speedMul` 一直是 1.0）。
   同類的「引力漩渦 +35%」也是。
2. **戰術興奮劑乘兩次** —— `eff.gold` 被乘進 `metaGoldMul`，而 `metaGoldMul` 開局會被
   天賦重算一次，等於平方。
3. **倉庫的「等效傷害」高估** —— 提示寫 `1 + 暴擊×(1+處決)`，但這是把引擎的
   `critMul = 2 + 處決` 誤當成 `1 + 處決`。正確期望值
   `(1-暴擊) + 暴擊×(2+處決) = 1 + 暴擊×(1+處決)`，同一套裝備顯示 ×1.98、實際 ×1.86。
   現在公式與引擎對齊，並把暴擊率夾在 100%（超過的部分沒有第二條路徑可以兌現）。
4. **生命上限靠 `baseMaxHp` 一個欄位兼兩職**（角色基礎 ＋ 局內被動），裝備的生命
   加成在買了防彈護甲之後會被覆寫掉。改成 `charMaxHp + gearHp + 被動` 三個來源明算。

`node tools/verify-gear.mjs`（22 項，Playwright 實機）逐條驗十種詞條真的改變對應欄位、
連續重算不會疊第二次、套裝 3/3 激活、傳奇特效的屬性加成生效、**實際開火傷害**
吃到 +30% 火力（無裝備 22 → 全裝備 29）、倉庫顯示值等於引擎期望值、興奮劑只乘一次。

## 🛠️ 技術架構

- **純原生 HTML5 + Canvas 2D + ES Modules**，零外部龐大依賴，隨開即玩。
- **Chiptune 動態合成音效與四聲部音樂引擎 (Web Audio API)**：
  - 參考 `chiptune-audio` 架構打造的純參數化合成音訊系統，**零外部音訊檔案、零網路載入耗時、100% 支援 PWA 離線遊玩**。
  - **24+ 種獨立微調音效預設**：覆蓋射擊 (`shoot`, `bolter`, `storm_bolter`, `turret_fire`)、命中揮砍 (`hit`, `slash`)、爆炸與震撼 (`explosion`)、元素反饋 (`freeze`, `flame`, `lightning`)、金幣與道具拾取 (`coin`, `heal`, `shield`, `powerup`, `pickup`)、警報與介面交互 (`alarm`, `boss_alert`, `click`, `select`, `error`)、升級與勝利號角 (`levelup`, `fanfare`, `win`, `gameover`)。支援完整 ADSR 振幅包絡線、音高滑頻 (pitch slide) 與立體聲聲相定位。
  - **AudioBuffer LRU 快取機制**：高頻音效預先合成並緩存，同參數組合瞬發重用，大幅降低每秒建立 AudioNode 節點的系統負擔，密集怪海下依然清脆無卡頓。

### PWA 換版（`version.json` 是唯一版本來源）

**症狀**：難度選擇上線後「**網頁版看得到、PWA 版看不到**」。

**原因**：`sw.js` 對導覽請求採「快取優先 + 背景更新」，所以已安裝的 App 改版後
**第一次開啟仍是舊版 HTML/CSS**（背景才偷偷換快取）；又因為 `sw.js` 位元組沒變，
瀏覽器不會 `updatefound`，也就沒有「有新版本」提示 —— 玩家會一直停在舊介面。

**修法**：
- 版本來源改為根目錄 **`version.json`**（發版只改這一個檔案的 `version`）。
  `sw.js` 於 install 時讀它決定快取名稱（`gaga-vN`）；`js/pwa.js` 以
  `sw.js?v=<version>` 註冊，版本一變就觸發更新檢查。
- **導覽請求與 `version.json` 改為網路優先**（離線才退回快取），因此「下一次開啟」
  就是新版介面，不必等第二次。其餘資源維持快取優先 + 背景更新。
- `activate` 除了清舊快取、`clients.claim()`，還會**廣播 `SW_UPDATED`**；
  `js/pwa.js` 收到就顯示「有新版本可用／重新載入」橫幅（涵蓋沒有 `updatefound` 的情境）。
- `version.json` 必須在預快取清單內（離線也要能讀到版本）。

`node tools/verify-pwa.mjs`（71 項）與 `node tools/verify-pwa-update.mjs`（7 項）把關：
後者會在 `/tmp` 複本上模擬一次發版（version.json 4→5＋HTML 塞 marker），驗證
**改版後下一次開啟就拿到新 HTML**、**SW 換版且舊快取被清掉**、**更新橫幅可重載**、
以及**更新後難度選擇在畫面上**。

### 全面引爆類炸彈（`tools/verify-bombs.mjs`）

回報「全面引爆的炸彈威力太大」。原本**四個**地方都是 `takeDamage(9999)` —— 撿到就是

| 里程碑 💣 震撼彈支援 | 全場 9999 | 同上 |
| 幸運輪盤 💣 全頻震盪波 | 全場 9999 | 同上 |

四個路徑共用 `config.js` 的 **`BOMB_TUNING`**（`fieldDamageRatio` / `fieldDamageMin` /

### 難度分級與祝福門檻（`tools/verify-balance.mjs`）

來自實機的回報，各自變成一條契約：

1. **「難度提升不夠」（第一輪）**：舊版困難只有血量 ×1.4／生成 ×1.4、惡夢 ×2.0／×1.8，
   而且只動了兩三個軸 —— 玩起來只是同一場打久一點。現在每一階同時在六個軸加壓：

   | 難度 | 敵人血量 | 玩家受傷 | 生成密度 | 菁英機率 | 敵人移速 | 金幣 | DNA |
   | :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
   | 🐣 輕鬆 | ×0.65 | ×0.5 | ×0.85 | — | — | ×0.75 | ×0.6 |
   | 🦆 標準 | 基準 | 基準 | 基準 | 基準 | 基準 | 基準 | 基準 |
   | 🔥 困難 | ×1.9 | ×1.7 | ×1.8 | ×1.6 | ×1.06 | ×1.40 | ×1.7 |
   | 💀 惡夢 | ×3.0 | ×2.4 | ×2.4 | ×2.2 | ×1.14 | ×1.9 | ×2.6 |
   | ☠️ 地獄 | ×4.2 | ×3.2 | ×3.0 | ×3.0 | ×1.14 | ×2.5 | ×3.6 |

   **這張表兩個模式都吃**，但套用點不同（v91）：

   | 軸 | 生存者 | 守塔 |
   | :--- | :--- | :--- |
   | 敵人血量 | `enemyScale()` 的血量曲線 | `TowerDefense.js:490` 雜兵、`:434` 首領（`TD_BOSS_HP = 0.45`） |
   | 玩家受傷 | `player.baseDamageTaken` | 同一條（英雄就是英雄） |
   | 生成密度 | `Spawner.js:140 interval /= spawnMul` | **波次佇列時間軸 `/ spawnMul`**（每波總數不變） |
   | 菁英機率 | `Spawner.js:172` 逐怪擲詞綴 | **`spawn()` 內逐怪擲詞綴**（前兩波 0、上限 45%） |
   | 敵人移速 | `enemyScale().speed` | `TD_SPEED × scale.speed`（`TowerDefense.js:496`） |
   | 金幣收益 | `Facilities.goldMul` | 同一條（`game.rules.goldMul`） |

   難度**解鎖**也是分模式的：`modes.js` 的 `difficultyLevels` 決定「前一階要全通關哪些關卡」——
   生存者 12 關（`LEVEL_ORDER` 扣掉沒有通關概念的 `endless`）、守塔 7 關（`TD_ORDER`）。
   守塔玩家打通七張圖就自己開下一階，不必回頭刷生存者。

2. **「難度還是不夠」（第二輪，玩家第二度回報）**：加壓到六個軸仍然不夠，量測後發現
   真正的瓶頸不是血量而是**傷害**。舊版雜兵傷害 = 基礎 × `min(3.5, 1 + 分鐘×0.1)`，
   20 分鐘就封頂 ×3.5；配上玩家 0.5 秒的無敵影格，後期雜兵的最大輸出只有約 **28 DPS**，
   而此時玩家有 100+ 血、50% 減傷與回復 —— 後期不是難，是**死不了**。

   兩處修正：
   - **新增第五階「地獄」**（血量級距 1.40×、受傷 1.33×，收益單調上調到 DNA ×3.6）。
     敵人移速刻意只給 ×1.14 —— 再往上會撞到 `enemyScale` 的 1.5× 封頂，變成不公平的
     追殺而不是難度；壓力改由傷害與密度提供。
   - **敵人傷害曲線改成「斜率 + 後期二次項 + 12 倍封頂」**：
     `min(12, min(5.5, 1 + 分鐘×0.14) × (1 + max(0, 分鐘-10)² × 0.010))`。
     10 分鐘前完全與舊版一致（3 分鐘 ×1.42）；20 分鐘 ×7.6、30 分鐘起封頂 ×12
     （單下約 96 點基礎傷害）。沒有最外層的 12 倍，40 分鐘會到 ×80 以上（單下 640 點），
     那已經不是「難」而是必死，會把走位與裝備的價值一起抹掉。

   契約：前 10 分鐘不受影響、傷害隨時間單調成長、20 分鐘 ≥6.5 倍、地獄每個軸都不弱於惡夢
   且血量級距 ≥1.3 倍、收益隨難度單調上升、**所有倍率鍵都必須是 `RULE_DEFAULTS` 認得的欄位**
   （打錯字會被 `mergeRules` 靜默丟掉）。

4. **「過了一個強度就基本不死」（第四輪，玩家第三度回報）**：第二輪把傷害拉到 12 倍封頂
   之後仍然會被回報「不死」，因為問題不在數字大小，而在**曲線形狀與通道數量**
   （完整分析見上方〈難度曲線為什麼是階梯〉）。這一輪的兩件事：

   - **把折線拉直**：`enemyDmgScale()` 取代原本的 `min(12, min(5.5, …) × 二次項)`。
     契約從「有硬封頂」改成**平滑度契約**：把 1~40 分鐘的傷害曲線做數值微分，
     相鄰分鐘的斜率變化必須 < 25%（實測最大 13.4%）；60 分鐘仍嚴格大於 40 分鐘
     （沒有硬封頂）；40 分鐘 ≤ 20 分鐘的 3 倍（次指數成長，不會變成必死）；
     單下傷害 40 分鐘 ≤ 150 點。
   - **補上不吃無敵影格的第二、第三條通道**：契約要求 `enemyScale().elem` 與
     `hazardDmgScale()` 都隨時間單調成長、且同樣平滑（斜率變化 < 25%）；
     每一種屬性都必須同時有護甲穿透、持續傷害與疊層上限（否則屬性只是換顏色）；
     **原始碼層級**確認屬性 DoT 的逐幀結算不經過 `takeDamage`（會被無敵影格擋掉）、
     確實有寫 `p.hp -=`、走 `damageTakenMul`（難度對屬性一樣有效）、
     而且 `takeDamage` 內真的會把元素交給 `applyElement`；
     最後要求回復泉／聖域有 `clearElements()` —— 沒有對策的壓力只是懲罰。

3. **「引力異常至少要 21 級之後再出現」**：它是「拾取範圍翻倍」的祝福，前期拿到等於讓
   「撿東西」這件事消失。改成在 `config.js` 標 `minLevel: 21`，過濾邏輯抽成純函式
   `blessingPool(ownedIds, playerLevel)`（`config.js` 無 import，Node 可直接測），
   `Progression.offerBlessingChoice` 改用它。契約：5／20 級抽不到、21／30 級抽得到、
   其餘祝福數量不受影響、已擁有的不會重複。

### 生成率曲線：第二個階梯（怪潮牆）

把傷害公式的折點與硬封頂拿掉之後，`playtest` 仍然在**每一張關卡**都量到同一個結構性
階梯：第 6~7 分鐘，敵人數從幾十隻衝到幾百隻。原因不在傷害，在**生成率**：

```
street  2.22 → 6.67 隻/秒（+200%）  第 6 分鐘
        6.67 → 15.38 隻/秒（+131%） 第 8 分鐘
core    6.67 → 13.64（+105%）       第 6 分鐘
subway  5.88 → 11.54（+96%）
```

波次表的 `interval` / `batch` 是**分段常數**，在邊界直接跳。於是「清場速率跟不上」的
那一分鐘一到，敵人數就衝到同屏上限 —— 玩家體感就是「怪潮毫無預警地湧上來」。
傷害曲線再平滑都救不了，因為它來自**生成量**而不是**每隻怪的強度**。

**兩層修正：**

1. **率當成連續量**（`levels.js` 的 `spawnRate()`）：生成率取「名目率在 ±90 秒窗內的
   移動平均」。用**對稱窗**而不是單邊內插是關鍵 —— 第一版只在進入新波次後往前混，
   結果只是把瞬時 +200% 拉成 72 秒的斜坡，每分鐘仍然 ×2.85。對稱窗讓爬升從邊界
   **前** 90 秒就開始。移動平均是單調函數的單調函數，所以曲線保證單調不減。
   `batch` 仍是整數（一次生幾隻是離散的），由 `interval` 吸收內插 ——
   每一波的敵人組成與主題完全不變，只有「生多快」被抹平。

2. **壓低後段的相鄰倍率**：把每波的生成率上限訂在**前一波的 1.5 倍**
   （73 個波次動了 48 個）。street 的後兩波 6.67 / 15.38 → **3.33 / 5.00**。
   為什麼敢砍這麼多：同屏上限 450 本來就會讓生成率飽和 —— 生成率超過清場速率之後，
   多出來的怪直接被上限丟掉。所以**降低生成率主要是把爬升拉長，不是降低峰值壓力**。

**契約（`verify-balance.mjs` 的 E 組）**：每個波次的率 ≤ 前一波 ×1.5、平滑後曲線
單調不減、任 30 秒內增幅 ≤ 60%、**8 分鐘的率仍 ≥ 2 分鐘的 3 倍**（拉平的是階梯，
不是把後期沒收；實測最低 3.69×）、`Spawner` 必須走 `spawnRate()`。

**實測（同一套指標、各 5 場、`--immortal`）：**

| | 基準 | 修正後 |
| :--- | ---: | ---: |
| 敵人數單分鐘最大跳動 | ×3.8 ~ ×7.3 | **×2.64** |
| 敵人數序列（每分鐘） | 7 17 24 16 20 **25 182** 396 450 415 | 10 22 53 93 110 **138 245** 384 413 300 |
| 不死平台期 | 無 | 無 |

基準的 25 → 182（一分鐘內 ×7）就是玩家說的「怪潮牆」；現在是 138 → 245（×1.8）。

**壓力曲線的跳動仍然偏高（×4~6.4），但工具只把它當提示、不當判定**：壓力＝人數 ×
單怪強度 × 玩家當下的走位，中間夾著「敵人開始真的碰到你」的門檻效應，
同一個版本跑兩次可以差一倍。人數爬升則直接由生成率決定 —— 那才是能修、也該修的量。

**還沒做**：修完之後最大的殘留跳動落在**第 4~5 分鐘的壓力爬升**（×4~6.4），
成因是 `OPENING.sparse` 的淡出疊上「敵人開始真的碰到你」的門檻效應 ——
一半是刻意的設計。2026-10-02 決定先不動，工單與驗收條件見
〈🚧 後續開發規劃 → 5. 第 4~5 分鐘的壓力爬升〉。

### 自動試玩機器人（`tools/playtest.mjs`）

平衡問題通常不是「某個數字不對」，而是**曲線的形狀**與**通道的數量** —— 這種東西看公式
看不出來，自己手動玩一次要十分鐘又不能重現。所以有一支會**真的把一場打完**的機器人：

```bash
node tools/playtest.mjs                                    # 標準／商業街／風箏走位／3 場
node tools/playtest.mjs --immortal --minutes=20             # 不死模式：量完整的壓力曲線
node tools/playtest.mjs --policy=brawl --build=defensive     # 貼臉打法＋生存取向選卡
node tools/playtest.mjs --difficulty=hell --assert           # 當成契約跑，失敗 exit 1
node tools/playtest.mjs --realtime --shots=/tmp/shots        # 真實時間＋每分鐘截圖（看畫面）
```

它跟其他三支的差別：`probe-enemy-pressure` 量單一機制、`verify-balance` 純 Node 量公式、
`playtest` 量**整場下來的體感曲線**。

**它回答的三個問題：**

| 問題 | 怎麼量 | 判定門檻 |
| :--- | :--- | :--- |
| 難度曲線平不平滑？ | 每分鐘的「承受傷害 ÷ 當時最大生命」＝**每分鐘吃掉幾 % 血** | 相鄰分鐘的相對跳動 ≤ `--max-jump`（預設 3） |
| 會不會進入不死平台期？ | 連續 3 分鐘壓力 < 5%/分（≈ 不動也要 20 分鐘才死）**且場上還有 > 20 隻怪** | 出現就 FAIL |
| 屬性／地形通道有沒有生效？ | 用 `_damageTaken` 差分把**衝擊傷害**與**逐幀持續傷害**分開統計 | 屬性層數峰值 ≥ 1 |

**為什麼用「% 最大生命／分鐘」而不是絕對 DPS**：250 HP 的 build 吃 3 DPS 跟 100 HP 的
build 吃 3 DPS 是完全不同的處境，而同一場裡 maxHp 一路在長 —— 絕對值會把曲線拉平。

**`--immortal` 為什麼必要**：正常模式下平均 2~4 分鐘就死了，晚期只剩一場還活著，
曲線會被存活者偏差截斷 —— 而「後期會不會不死」正好要看晚期。不死模式只攔 `onLethal`
把血補滿，傷害量測（走 `_damageTaken`）完全不受影響，於是 3 場都能貢獻完整 12 分鐘的樣本。

**可以重現到什麼程度**：種子在頁面載入前就固定整條亂數序列（連「載入後到我接手之前」
那幾幀真實 rAF 都關掉），但**不是逐位元可重現** —— 遊戲內部仍有讀真實時間的路徑
（音效引擎的 `AudioContext.currentTime`、自適應效能），跨執行會小幅漂移。
看跨場次中位數，不要依賴單場數字。

**它實際抓到的東西**（第一次跑就抓到，比我手動玩有效）：

```
敵人數爬升：單分鐘最大跳動 ×2.64（第 6→7 分）　✅
壓力曲線：前後 2 分鐘窗的最大跳動 ×5.79（第 5~6 分）（僅供參考 —— 壓力含玩家清場能力的
          門檻效應，比值天生吵）
  ⚠️ （提示，不判定）壓力曲線的前後窗跳動 ×5.79 @ 第 5~6 分 高於 3
```

工具上線的第一次跑就抓到**同屏敵人數在 6~8 分鐘從 25 衝到 182（一分鐘內 ×7）再到上限
450** —— 這件事用公式或單一機制探針都看不出來，只有整場打下來才會現形。
它把診斷也一起印出來（「這不是傷害公式，是波次表與生成間隔」），照著修就成了
〈生成率曲線：第二個階梯〉那一節，修完 ×7 → ×2.64。

**目前還紅著的一項**：壓力曲線在**第 4~5 分鐘**仍有 ×4~6.4 的殘留跳動，
`--assert` 會把它印成 `⚠️` 提示但不判定。要追這條請先讀
〈🚧 後續開發規劃 → 5. 第 4~5 分鐘的壓力爬升〉—— 那裡寫清楚了為什麼一半是設計、
以及動手時不能踩的兩個坑（不要把敵人數壓成平的、不要動傷害倍率）。

### 難度選擇的可見性（`tools/verify-difficulty-ui.mjs`）

全域難度選擇（輕鬆／標準／困難／惡夢／地獄）上線後放在關卡清單後面，而 11 張關卡卡＋特工卡
讓開始面板內容高達約 2000px（可見區只有 ~770px），難度選單實際落在 y≈1534 —— 玩家必須
在面板內捲動才看得到，回報「我看不到難度選擇」。

修法：把難度選單與出擊鈕收進**黏在面板底部的操作列**（`position: sticky`），並把原生
`<select>` 改成主題樣式（深底、青框、≥44px 點擊高度），下方即時顯示該難度實際乘上的
規則倍率（讀 `DIFFICULTIES`，不與平衡脫節）。

`node tools/verify-difficulty-ui.mjs` 會在 1280×720、1280×800、390×844 三種視窗各驗 7 項：
選單與出擊鈕必須在**首屏可見**、五個選項齊全且標 DNA 倍率（含新增的地獄）、切換後存檔與說明同步、
以及**實際進入遊戲後 `game.rules.enemyHpMul` 真的等於 1.9**（困難）。

**v91 追加第 4 段（`probeModes()`，38 項）**：難度分模式之後，同一支測試再走一遍
「生存者地獄 → 切到守塔 → 守塔只解鎖輕鬆」的完整路徑：切換模式後下拉要換成**守塔自己那一份**
（不被生存者的地獄帶走）、鎖定文字的進度是 `/7` 且標「（守塔）」、說明多出
「密度＝同一波的怪更密（總數不變）」、在守塔選惡夢只寫 `tdDifficulty`（`difficulty` 仍是地獄）、
切回生存者仍是地獄，最後按出擊確認 `game.diffKey === 'nightmare'` 且 `rules.enemyHpMul` 與
`DIFFICULTIES.nightmare` 一致。這一段是**唯一**守得住「兩份難度沒有互相污染」的地方 ——
純資料層的斷言看不出「下拉被另一模式覆寫」。

**第 4~5 分鐘之間**：前 2 分鐘窗的壓力平均 2.1 DPS、後 2 分鐘窗 13.4 DPS，比值 ×6.4
（同一份程式碼重跑，這個比值會落在 ×4~6.4 —— 壓力天生吵，看形狀不要看小數第二位）：

```
  1 分   0.4 DPS   24%/分   敵  10
  2 分   2.0 DPS  119%/分   敵  22
  3 分   1.9 DPS  116%/分   敵  53
  4 分   2.3 DPS  138%/分   敵  93   ← 前四分鐘壓力幾乎是平的
  5 分   9.4 DPS  565%/分   敵 110   ← 這一分鐘突然有感
  6 分  17.3 DPS 1038%/分   敵 138
```

**兩個成因疊在一起，只有一個是 bug：**

1. **`OPENING.sparse = 2.2` 的淡出**（`levels.js`，前 180 秒把生成間隔拉長 2.2 倍）。
   這是刻意的：開場要安靜，讓玩家先熟悉操作。它本身是 smoothstep、兩端導數為 0。
2. **「敵人開始真的碰到你」的門檻效應**：對照上面那張表，前窗的敵人數平均是 73 隻、
   後窗 124 隻（**+70%**），但壓力是 2.1 → 13.4 DPS（**×6.4**）——
   壓力長得比人數快一個量級。原因是第 3~4 分鐘的敵人大多走不到玩家面前
   （清場速率還跟得上），第 5 分鐘起牠們開始真的碰到你。
   **所以這一段不是生成率的問題**：同期生成率只增加了約 50%（E 組契約保證的上限），
   人數也只增加 70%，多出來的 6.4 倍是「接觸率」而不是「量」。
   `playtest` 的報告把這件事寫明了：壓力＝人數 × 單怪強度 × 玩家當下的走位，
   中間夾著門檻效應，所以工具**只把它當提示、不當判定**（判定用的是「敵人數爬升」）。
   動手前請先確認你要修的是「前四分鐘太平」還是「第五分鐘太陡」—— 這兩件事的解法不同。

**要動的話，三個方向（依風險排序）：**

| 方向 | 改哪裡 | 代價 |
| :--- | :--- | :--- |
| ① 把 `OPENING.dur` 180 → 300 秒、`sparse` 2.2 → 1.8 | `js/levels.js` 的 `OPENING` | 最安全（只動兩個常數），但開場會稍微熱鬧一點 |
| ② 在 ~200 秒插一波中間波次，把 120→240 秒那段補密 | `js/levels.js` 各關 `waves` | 要逐關調，且**必須重跑 E 組契約**（每波 ≤ 前一波 ×1.5） |
| ③ 接受它是設計 | 無 | 前四分鐘本來就該是暖場 |

**驗收條件（三條都要過，缺一不可）：**

- `node tools/playtest.mjs --immortal --trials=5` 的壓力窗跳動 ≤ ×3（目前 ×4~6.4）
- 同一支的「敵人數爬升」仍 ≤ ×3（目前 ×2.64，**不可以為了壓壓力而把它壓成平的**）
- `node tools/verify-balance.mjs` 的 E 組全綠 —— 特別是 **E4「8 分鐘的率 ≥ 2 分鐘的 3 倍」**：
  它存在的目的就是防止「為了拉平曲線，把後期一起沒收」，那會反過來製造出
  「不死平台期」（正是玩家最早回報的那件事）

**不要做的事（兩個都很容易誤判）：**

- **不要調 `enemyScale` 的傷害倍率。** 調傷害是把整條曲線一起往上推，第 5 分鐘之後
  的每一分鐘都會跟著變陡 —— 跳動不會消失，只是換地方。
- **不要只補生成率。** 同期生成率只增加約 50%、人數增加 70%，壓力卻 ×6.4 ——
  多出來的那一個量級是**接觸率**（敵人開始走得到你面前），不是量。
  往「量」的方向補只會讓前四分鐘不再安靜，卻不一定拉平那一跳。
  真要動，先量「敵人實際接觸到玩家的比例」，別從生成率下手。
